# 02. 施工路线图：文献资产与收纳中心

## 阶段门

- **结论**：2026-08-26 通过阶段门，进入施工。
- **前置**：工单 06、07 已归档；`LiteratureItem` 与既有 PDF 文件关联可用。
- **施工协议**：工单 08 只负责资产层和收纳，不提前实现阅读会话、全文索引、笔记或多数据源合并。

## 里程碑

| 阶段 | 交付物 | 关闭标准 |
|---|---|---|
| M1 | DocumentAsset 模型与兼容读取 | 新旧 JSON 可读；资产 UUID、类型、存储方式、状态和元数据语义稳定；core 单测覆盖 |
| M2 | Vault 收纳、哈希与重复处理 | PDF 收入 `files/<item_id>/<asset_id>-...`；SHA-256 正确；同条目重复不复制；失败不破坏 |
| M3 | 资产管理与外部链接迁移 | 列表、健康状态、移除、设类型、外部转库内副本闭环；后端命令受控 |
| M4 | 回归、迁移与 portable 验收 | 复制库验证、旧 JSON 验证、全量命令通过；不同干事初审通过后由经理终审 |

## M1 实施细则

1. 在 core 定义 `DocumentAsset`、`DocumentAssetKind`、`DocumentAssetStorageKind` 和可计算状态。
2. 为 `document_assets.json` 增加原子读写 API。
3. 为工单 07 的旧 `files` 提供兼容读取，不强制一次性迁移。
4. 保持 `LiteratureItem` 的现有序列化兼容，并明确新旧数据的权威顺序。

## M2 实施细则

1. 收纳前验证存在、普通文件和 `.pdf` 扩展名。
2. 流式或分块计算 SHA-256，避免不必要的整文件内存复制。
3. 以 `asset_id` 生成目标路径，不覆盖既有文件。
4. 同条目相同哈希返回可识别的重复结果，不创建第二份资产。
5. 复制、哈希、用户数据发布任一步失败时清理本轮临时物，不破坏既有资产。

## M3 实施细则

1. Tauri 命令只接受 `item_id`、`asset_id` 和文件选择结果，不接受任意打开路径。
2. Reading 通过资产 ID 打开，不再依赖旧 `file_id` 作为新能力的唯一入口。
3. Vault 工作区显示资产类型、位置、大小、哈希摘要和当前健康状态。
4. 外部链接转库内副本成功后产生新的 Vault 资产；原外部资产保留，移除由用户显式完成。
5. 移除资产只移除关系和资产记录，不默认删除物理文件。

## M4 实施细则

1. 添加公共 API 集成测试：复制 Vault、旧 JSON、重复哈希、外部断链、缺失文件和失败清理。
2. 检查 `manifest.json` 与 Source tables 未出现用户资产数据。
3. 复跑：

```powershell
cargo test -p cistella-core
cargo check -p cistella-desktop
pnpm build
```

4. 施工交付后必须由不同干事独立初审；��审发现问题回到对应里程碑返工，复审通过后再由经理终审归档。

## 施工协议

- 每个里程碑执行“实施 → 不同干事初审 → 必要返工 → 复审”。
- 任何改变旧 JSON 解释、Vault 目录契约或用户文件删除语义的偏离，必须记入施工日志并由经理裁定。
- 不得以“兼容旧字段”为理由无限扩大范围；旧字段只保留到明确迁移工单。
