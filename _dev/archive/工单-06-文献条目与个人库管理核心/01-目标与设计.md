# 01. 目标与设计：文献条目与个人库管理核心

## 1. 工单目标

在稳定的 Vault 之上建立 cistella 的用户文献条目层，使系统从“来源数据分析”进入“个人文献保管与组织”。

## 2. 北极星

用户收进库中的不是一张来源数据表，而是可被收藏、组织、检索、阅读和持续维护的个人文献资产。

## 3. 范围边界

### 本工单包含

- 文献条目的第一版用户模型。
- 来源记录与用户意图的分离。
- 文献条目浏览、筛选与基础组织。
- 收藏、标签、阅读状态等最小个人管理能力。
- 文献条目与 Vault 的归属关系。
- 为后续 Reading 工单提供稳定的条目标识与状态入口。

### 本工单不包含

- 阅读器与笔记编辑器。
- 多来源合并与复杂去重。
- 云同步、协作与账号系统。
- 高级全文语义检索。
- Source 分析工作区的增强功能。

## 4. 设计方向

文献条目属于用户库内的长期资产；来源数据是可追溯的外部事实；用户状态、标签与收藏是用户意图。两者必须可以分别演进，不能把来源字段直接当作用户条目模型。

## 5. 决策结论

### 5.1 条目标识

- 每个文献条目使用 cistella 自己生成的 UUID 作为稳定 `item_id`。
- `item_id` 不由 OpenAlex ID、DOI 或其他外部标识替代。
- 外部标识属于条目的可更新事实，不能改变条目标识。

### 5.2 来源关系

- 条目与来源记录按一对多关系设计。
- MVP 允许零个、一个或多个来源记录；首次实现可以只创建一个来源记录。
- 来源记录至少保存来源名称、外部标识和原始定位信息。
- 本工单不做跨来源自动合并；多个来源记录只表达可追溯关系。

### 5.3 用户字段

MVP 用户字段固定为：

- `title`：用户可编辑标题。
- `authors`：作者文本列表。
- `published_year`：可选年份。
- `item_type`：article、book、chapter、other。
- `favorite`：收藏状态。
- `reading_status`：inbox、reading、finished、archived。
- `tags`：用户标签列表。

本工单不引入笔记正文、全文内容或复杂自定义字段。

### 5.4 数据落位

- 用户条目存放在 Vault 内固定的 `user/literature_items.json`。
- 该文件属于可携带的用户数据，不进入分析 table manifest，不被 Source 查询覆盖。
- 写入采用临时文件加替换的原子更新方式；文件不存在时视为空库。
- manifest 继续描述分析库结构；用户条目通过 Vault API 访问。

### 5.5 与工作区的边界

- Reading 工作区在本工单只获得条目浏览、创建、编辑基础入口和阅读状态切换。
- Source 工作区不直接改写用户条目。
- 后续 Reading 工单再承接文件打开、笔记、标注与阅读视图。

## 6. 关键交付物

- 文献条目模型与来源记录模型。
- Vault 内用户条目的可携带持久化文件。
- 条目浏览、创建、编辑、收藏、标签和状态切换的最小闭环。
- 为 Reading 工单提供稳定条目标识和 API。

## 7. 成功标准

- 用户可以在 Vault 内创建、浏览、编辑和组织自己的文献条目。
- 用户状态与来源事实分离，来源变化不会覆盖用户意图。
- 条目文件可随 Vault 复制、备份和迁移。
- 后续 Reading 工单可以直接引用 `item_id` 与 `reading_status`。
- 不把 OpenAlex 或任何单一来源写成条目模型的前提。

## 8. 施工准入判定

### A 层

cistella 的核心资产从来源级数据扩展为用户文献条目；这一方向已与总路线一致，不再新增方向问题。

### B 层

条目标识、来源关系、用户字段、物理落位和 Source/Reading 边界已由经理拍板，见本节决策结论。

### C 层

JSON 序列化细节、Tauri command 命名、React 组件拆分、错误文案和临时文件命名交由干事按默认方案实现，偏离通过施工日志回填。
