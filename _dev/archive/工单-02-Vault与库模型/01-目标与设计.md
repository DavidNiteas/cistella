# 02. 目标与设计：Vault 与库模型

## 1. 工单目标

定义 cistella 的本地库模型，使其成为可复制、可迁移、可备份、可长期保存的核心对象。

## 2. 北极星

用户打开任意一个 cistella 库时，感知到的是一套完整、稳定、可搬运的个人文献资产，而不是一个临时数据目录。

## 3. 范围边界

### 本工单包含
- 库/Vault 的核心边界与命名
- manifest 与库元数据的职责边界
- 原始数据、标准化数据、索引、缓存、导出物、用户数据的分层
- portable 与复制即走的产品约束
- 库的打开、识别、连接与状态感知

### 本工单不包含
- 具体导入流程实现
- 桌面工作区导航细节
- Source 分析界面的交互细节
- 多数据源融合策略

这些内容留给后续工单。

## 4. 设计结论

库是系统的第一性对象。所有后续工作区和导入能力都必须围绕这个对象组织，而不是围绕某个数据源目录组织。

## 5. 关键交付物

- 库模型定义清单
- 目录与命名规范
- manifest 职责说明
- 数据分层说明
- portable 约束说明

## 6. 成功标准

- 库对象可以独立描述与识别
- 库具备可迁移和可备份的语义
- 后续工单能直接引用库模型而无需重新解释
- 不会把 OpenAlex 语义写进核心库定义里

## 7. 决策结论

- 用户可以维护多个独立 Vault；当前桌面壳层以最近库列表承接多库入口。
- MVP 阶段一个 Vault 以一个来源实体/快照为主；多来源并存留给后续统一条目模型工单，不在本工单隐式扩张。
- 用户数据与派生数据逻辑隔离：用户意图、标签、笔记、阅读状态属于用户层；缓存、索引、导出物属于可重建派生层。
- manifest 内部文件路径使用相对路径；source provenance 的 input_path 仅作溯源记录，不是打开 Vault 的运行时依赖，允许保留导入时绝对路径。
- Dataset 兼容别名暂时保留，作为施工期兼容层，不再新增 Dataset 主 API。

## 8. 施工准入判定

### 已满足的施工前条件
- Vault 作为系统第一性对象的定位已明确。
- manifest、table、source provenance 的职责边界已给出主结论。
- portable、复制即走、可备份的约束已写入范围。
- 下游依赖已识别：桌面壳层、导入适配器、Source 工作区。

### 施工期关闭标准
- Vault / manifest / table 的职责边界不再引入新的方向性争议。
- 兼容别名是否保留，只在施工期按偏离申请处理。
- 用户数据、派生数据、导出物的边界在实现中保持一致。


## 9. 数据边界约束

### 8.1 manifest 的职责
- 只描述一个库是什么、来自哪里、包含什么表。
- 不承载查询状态、界面状态或分析结论。
- 不直接记录用户交互历史。

### 8.2 table manifest 的职责
- 只描述单表的物理布局与可用文件。
- 记录 parquet / arrow 的存在、路径和体量。
- 不记录查询条件、排行结果或导出历史。

### 8.3 source provenance 的职责
- 只描述库的外部来源与输入路径。
- 记录 snapshot、来源名称和接入实体。
- 不承担分析派生结果的保存。

### 8.4 派生数据的归属
- 索引、缓存、导出物属于库内派生资产。
- 这些资产可以被重建，但重建规则必须可追溯。
- 任何不可重建的业务含义都不应藏在派生文件里。
