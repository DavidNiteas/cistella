## 2026-08-26｜M1 第五次返工执行记录

### 触发问题

独立复审确认第四次返工的两个 OS 子进程虽然由父进程连续 `spawn`，但没有跨进程 ready/start rendezvous。A 可能完整更新并退出后 B 才开始，原测试仍可得到“一胜一冲突”，不能排除顺序假象。该问题阻断 M1 经理终审。

### 实施协议

- 在测试进程中创建一次性 UUID 命名 Windows Event：ready-A、ready-B、shared-start、started-A、started-B；事件位于 `Local\cistella-m1-rendezvous-...` 内核对象命名空间，不在 Vault 目录中创建控制文件。
- 每个子进程继承事件名和相同的 `CISTELLA_M1_CAS_CHILD_REVISION`，先 `Vault::open`，打开 ready/start/started 事件，signal 自己的 ready，然后阻塞于共享 start。
- 父进程等待 A/B ready 均 signaled 后，才 signal 一次 shared start。
- 子进程从 shared start 返回后，在实际 `update_note` 前一条语句 signal 自己的 started。父进程等待 A/B started 均 signaled 后，才对任一子进程调用 `wait`。因此测试协议明确证明两个独立进程都已打开 Vault、收到统一起跑、并已抵达更新调用前，而不是靠 `sleep`、spawn 顺序或 wait 顺序。
- 子进程完成更新后写出结果标记；父进程断言恰好一个 `ok`、一个 `conflict`，最终 Markdown 内容属于胜者，Notes 目录只剩 `<note_id>.md`，没有临时或锁文件。

### P2 审查与收口

- 原 `D:(A;;GA;;;IU)(A;;GA;;;AU)` 会把 Global mutex 完全访问权授予所有已认证用户，存在抢先创建或长期持锁的 DoS 面。
- 本次将 SDDL 收紧为 `D:(A;;GA;;;OW)`（Owner Rights）。同一 Windows 账户的多个 session 仍通过 `Global` 共享；无关账户不再获得显式 GA。保留 vault_id + note_id 锁键、30 秒等待上限、`NoteCasLockUnavailable` 失败语义，绝不退回 Local 或无锁更新。系统策略拒绝 owner 创建/打开 Global mutex 时仍然失败关闭。
- 该测试不伪造跨 Terminal Services session；当前环境未提供 session 隔离测试，限制继续登记。

## 2026-08-26｜M1 第六次返工：锁内竞争证据与 IPC 隔离

### 触发问题

第五次返工复审确认：子进程仅在 `update_note` 前发送 `started` 通知，父进程无法证明一个进程已经持有 CAS mutex 且另一个进程已经进入同一 mutex 的等待队列；A 可能通知、完整更新后 B 才通知，测试仍会通过。同时，`child-a.result` / `child-b.result` 写在被测 Vault 根目录，违反“IPC 不污染 Vault”。

### 实施

- 在 `secure_user_records::with_note_cas_lock` 中加入仅 debug 构建、由 `CISTELLA_M1_CAS_TEST_HOOK=1` 激活的内部测试 hook。hook 打开父进程创建的三个命名 Event：`lock-held`、`waiter-attempted`、`commit-barrier`。
- hook 激活时先对 Global mutex 做零时探测：获得 `WAIT_OBJECT_0/WAIT_ABANDONED` 的进程报告 `lock-held` 并在提交前等待 `commit-barrier`；探测得到 `WAIT_TIMEOUT` 的进程报告 `waiter-attempted`，随后使用原有 30 秒有界等待。父进程只有在两个事件均到达后才释放 `commit-barrier`，因此协议证明真实的 holder/waiter 竞争，不依赖 sleep、spawn 顺序或 wait 顺序。
- 保持生产默认路径不变：未激活 hook 时仍直接进行 30 秒有界 Global mutex 等待；hook 没有公共 API、没有锁文件或 Vault 文件。
- 将两个结果 marker 改写到 Vault 外独立临时 IPC 目录；ready、锁竞争和提交屏障均为命名 Event，不写入 Vault。
- 增加 `ProcessCasCleanup` RAII guard，持有根目录、IPC 目录和子进程；发生 panic、超时、断言失败或子进程异常时，Drop 尝试 kill/reap 子进程并删除 IPC/Vault 临时目录。

## 2026-08-26｜M1 第七次返工：有界子进程回收与测试 hook 隔离

### 触发问题

第六次独立复审指出 `ProcessCasCleanup.wait_all()` 逐个调用 `Child::wait()` 无超时。commit-barrier 释放后若任一子进程挂死，父进程将永久阻塞，`Drop` 无法执行；同时 Debug 环境变量 hook 尚未做到严格的 test-only 激活。

### 实施变更

- 将 `wait_all` 改为接受总超时的 `try_wait` 轮询。所有子进程分别跟踪退出状态；任一轮询错误或总时限到期时，立即进入 `terminate_and_reap`，kill 全部仍存活子进程，并在 2 秒有界窗口内持续 `try_wait` 回收，绝不使用无界 `Child::wait()`。这同时处理“一个已退出、另一个仍存活”的情况。
- `ProcessCasCleanup::Drop` 复用有界 `terminate_and_reap`，然后删除 IPC 临时目录与 Vault 临时目录；因此 panic、事件超时、断言失败和正常超时均不会把父进程卡在无界等待上。
- 增加 `m1_process_cas_timeout_kills_reaps_and_cleans_up` 故障注入测试：子进程收到 commit-barrier 后执行测试专用长睡眠；父进程以 750ms 总时限等待，收到 `TimedOut` 后完成 kill/reap，显式断言在 3 秒内返回并且 Vault/IPC 临时目录不存在。结果文件和事件均位于 Vault 外，不污染权威目录。
- 将 hook 激活条件收紧为 Debug + child marker + `CISTELLA_M1_CAS_TEST_HOOK=1` + 本轮 UUID token；marker 已设置但 token 不合法时返回 `NoteCasLockUnavailable`，不静默进入测试等待。普通 Debug Desktop 只有通用环境变量时不会激活 hook。
- 保留 Global owner-only ACL、`sha256(vault_id)+note_id` 命名、30 秒产品锁等待、handle-rooted relative native I/O、目录解析边界校验、严格 annotation JSON、锁内 revision CAS 及 M1 范围。

## 2026-08-27｜M1 第七次返工续作：P1/P2 阻断项收口

### 触发问题

第七次返工后的独立复审登记两项阻断：
- P1：`ProcessCasCleanup::terminate_and_reap` 未在返回前确认全部子进程已退出，`Drop` 可能仍在子进程存活时删除 IPC/Vault 临时目录。

### 实施变更

#### P1：有界回收并确认全部退出后再清理

- 将 `ProcessCasCleanup::terminate_and_reap` 返回类型改为 `std::io::Result<()>`。
- 终止全部子进程后，以 5 秒有界总超时轮询 `try_wait()`，只有确认每个子进程句柄都已退出才返回 `Ok(())`；否则返回 `Err(TimedOut)`。
- `Drop` 仅在 `terminate_and_reap()` 成功后才删除 `ipc` 与 `root`；失败时保留目录，避免在子进程仍持句柄时清理。
- `wait_all` 在超时或轮询错误分支中传播 `terminate_and_reap()` 的结果。
- 在 `m1_process_cas_timeout_kills_reaps_and_cleans_up` 中新增显式断言：
  - `wait_all(750ms)` 超时后调用 `cleanup.terminate_and_reap().expect(...)`；
  - 调用 `cleanup.all_reaped()` 确认两个子进程句柄都已退出；
  - `drop(cleanup)` 后再断言 `root`、`ipc` 目录与结果文件均不存在。
- 保留“故障注入测试总耗时 < 3 秒”断言不变。

- 在 `secure_user_records.rs` 的 Windows `platform` 模块内新建 `#[cfg(test)] mod cas_test_hook`，将 `TestHookEvents`、hook 环境变量解析、零时探测、事件信号代码全部移入其中。
