## M1 第三次返工验收（待新的不同实例复审）

- 初审新 P1 已闭合：`update_note`、`archive_note`、`unarchive_note` 不再在锁外读取/比较 revision 后再写入。三类操作现在经 `SecureUserRecords::with_note_cas_lock(note_id, ...)` 进入同一跨线程、跨进程临界区，并在锁内重新通过已固定 Vault 根目录 handle → `user/notes` 目录 handle 的相对 native 读取取得原始 Markdown、计算 revision、核对 `expected_revision`、写入临时文件并使用目录 handle 相对原子替换；第二个同 revision 请求在获得锁后必然看到新 revision 并返回 `NoteConflict`。
- 锁设计：Windows 使用以 `note_id` 导出的命名内核 mutex（`Local\cistella-note-cas-<uuid>`），不创建/解析任何 lock 文件路径、不暴露 Vault 路径、不进入列举或写入白名单；正常离开由 guard 释放，持锁进程崩溃由内核释放，避免遗留 lock/temp 权威文件。Notes 权威记录的读/写/替换仍全部只走既有 `SecureUserRecords` handle-rooted native I/O，未退回普通 Path API。非 Windows 平台继续 fail closed，未引入普通 Path fallback。
- 新增确定性并发测试：两个独立 `Vault` 实例使用同一初始 revision，在 barrier 同步后并发调用 `update_note`；断言仅一个成功、另一个 `NoteConflict`、最终记录等于胜者且 `user/notes/` 仅保留 `<note_id>.md`。同一测试还以两个独立实例并发 `unarchive_note` 证明归档状态迁移复用同一 CAS 锁机制。
