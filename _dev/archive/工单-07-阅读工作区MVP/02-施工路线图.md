# 02. 施工路线图：阅读工作区 MVP

## 阶段门

- **结论**：2026-08-26 通过阶段门，进入施工。
- **依据**：A 层已授权经理收口；B 层数据模型、portable 路径、文件类型、打开边界、默认规则和失败语义均已写入 `01-目标与设计.md`。

## 施工阶段

| 阶段 | 交付物 | 关闭标准 |
|---|---|---|
| M1 | core 文件关联模型与路径安全 API | 旧 JSON 兼容；库内复制、外部链接、设默认、删除与解析均有单测 |
| M2 | Tauri 阅读命令与系统打开 | 后端仅按 item/file 标识解析受控 PDF 路径；打开失败不写用户状态 |
| M3 | Reading 工作区闭环 | 添加库内副本/外部链接、文件列表、默认文件、打开、删除与失败反馈可用 |
| M4 | 回归与归档验收 | 三条验收命令通过；路径逃逸、库复制和失败不破坏得到验证 |

## 实施细则

### M1：core

1. 在 `literature.rs` 定义 `LiteratureFileKind`、`LiteratureFileRef`，并给 `files`、`default_file_id` 加 `serde(default)`。
2. 新增 API：添加 Vault 副本、添加外部链接、移除关联、设置默认、解析打开路径。
3. Vault 副本统一进入 `files/<item_id>/`；只接受存在的 `.pdf` 源文件。
4. 若目标文件名冲突，干事采用不会覆盖既有文件的唯一命名；任何复制或元数据写入失败都不得破坏现有 `literature_items.json`。
5. 路径验证必须在写入和打开前执行；禁止用户数据路径逃逸。

### M2：desktop backend

1. 扩展请求/响应 JSON，传递 `itemId` 和 `fileId`，不接受前端传入的任意待打开路径。
2. 添加文件选择仅接受 PDF。
3. 系统打开应由 Tauri 后端对受控路径发起；如需引入官方 Tauri 打开插件，限于本能力所需最小依赖与权限。
4. 打开成功仅返回“请求已发起”；不得自动写回 `reading_status`。

### M3：frontend

1. 编辑器提供“加入 Vault”和“仅链接外部文件”，并在外部项上显示不可携带提示。
2. 条目卡片提供打开默认文件；无默认时明确提示。
3. 文件列表提供打开、设为默认、移除操作与可理解的失败反馈。
4. 切换/恢复 Vault 后重新加载条目及文件关联；无 Vault 时清空旧状态。

### M4：验证

```powershell
cargo test -p cistella-core
cargo check -p cistella-desktop
pnpm build
```

另行验证：

- 旧格式 JSON 可读取。
- `../`、绝对库内路径等逃逸值被拒绝。
- 加入 Vault 后文件落到 `files/<item_id>/`，移动/复制 Vault 后仍可解析。
- 外部链接不被伪装为 portable。
- 文件缺失或打开失败不改变条目、默认文件或阅读状态。

## 施工协议

- 不修改工单 06 已拍板的条目标识与基础字段语义。
- 用户数据继续采用同目录临时文件 + 原子替换。
- 不扩大到内置阅读器、笔记、标注、全文检索或非 PDF 格式。
- 偏离涉及 Vault 目录契约、新运行时依赖或公共 API 破坏时，干事必须写入施工日志并交经理裁定。
