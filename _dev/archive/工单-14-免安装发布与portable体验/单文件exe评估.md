# 单文件 exe / 离线安装包可行性评估

## 1. 当前 Tauri 架构下是否可行

### 1.1 Tauri 原生产物形态

Tauri v2 在 Windows 上的标准发布产物是：

- 一个主可执行文件（`cistella.exe`）。
- 一个 WebView2 加载器与相关运行时依赖。
- 前端静态资源（HTML/JS/CSS）通常通过 Tauri 的「内嵌资源（embedded assets）」机制打包进二进制，因此单独运行时不需要额外的 `dist/` 目录。

因此，**从「能否只给用户一个 exe」这个最狭义的问题来看，答案是：可以**，因为 Tauri 的 release exe 本身就是一个独立的可执行文件，前端资源已经内嵌。

### 1.2 与「单文件 exe」的常见理解之间的差异

用户或市场常说的「单文件 exe」通常还隐含以下期望：

1. 不需要安装 WebView2。
2. 不需要任何外部 DLL、运行时或系统组件。
3. 文件体积足够小，可以随手复制。
4. 启动速度与原生应用相当。

Tauri 目前**无法同时满足以上全部期望**：

- WebView2 是 Windows 10/11 的系统组件，大多数机器已预装；但如果目标环境缺失，应用会无法启动或提示安装。
- Tauri 可以通过 `--targets nsis` 生成安装包，但这不是单文件 exe。
- 使用 Enigma Virtual Box 等工具把 exe、DLL、运行时一起打包成一个自解压 exe 技术上可行，但这会破坏代码签名、更新机制和可信度。

## 2. 风险分析

| 维度 | 风险描述 | 影响程度 |
|---|---|---|
| 文件体积 | 即使前端资源内嵌，Tauri 应用体积仍包括 Rust 二进制 + WebView2 桥接层。当前 release exe 约数十 MB；若再打包所有运行时，体积会进一步增加。 | 中 |
| 启动速度 | 单文件自解压方案需要在启动时把资源释放到临时目录，会显著拖慢冷启动。 | 高 |
| 兼容性 | WebView2 版本差异、Windows 版本差异、安全策略差异可能导致表现不一致。单文件化并不能消除这些差异。 | 中 |
| 维护成本 | 需要引入额外工具链（如 Enigma、7z SFX、自定义 loader）并维护打包脚本；与 Tauri 标准流程不兼容。 | 高 |
| 自动更新 | Tauri 的 updater 插件默认基于签名后的安装包或 archive。单文件 exe 会让增量更新、签名校验变得困难。 | 高 |
| 安全与信任 | 自解压 / 打包后的单文件 exe 更容易被杀软误报；且不利于代码签名验证。 | 高 |

## 3. 决策建议

**建议延后或不做独立的「单文件 exe」方案，理由如下：**

1. **Tauri 已经提供了足够的免安装体验**：portable zip 解压即可运行，不需要安装程序写入系统目录，已经满足工单 14「免安装发布与 portable 体验」的核心目标。
2. **NSIS 安装包覆盖需要安装程序的场景**：对于需要开始菜单快捷方式、卸载入口的用户，NSIS setup.exe 是标准且可维护的方案。
3. **单文件化收益有限、风险显著**：它并不能真正消除 WebView2 依赖，反而会引入自解压延迟、杀软误报、更新困难等问题。
4. **维护成本与团队规模不匹配**：当前项目没有专门的发布工程师，保持 Tauri 标准构建流程可以降低长期维护负担。

## 4. 可替代的中间方案（未来可选）

如果未来仍有强烈需求，可考虑以下成本更低的折中方案：

- **继续优化 portable zip**：保持当前 `cistella-portable/` 标记 + `README-portable.txt`，让用户解压即用。
- **代码签名**：申请 OV/EV 证书后对 MSI / NSIS / portable exe 签名，减少 SmartScreen 拦截，提升信任度。
- **使用 Tauri 官方 updater**：当项目进入需要自动更新阶段时，启用 Tauri updater 插件，使用签名后的 NSIS 安装包或 zip 进行增量更新。

## 5. 结论

- **当前阶段**：不引入单文件 exe / 离线安装包方案。
- **核心发布形态**：继续以 MSI + NSIS setup + portable zip 三种产物覆盖不同使用场景。
