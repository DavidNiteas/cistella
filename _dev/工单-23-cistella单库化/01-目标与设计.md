# 工单 23：cistella 单库化

## 1. 工单目标

将 cistella 的用户心智、前端工作流与后端聚合模型收敛为“单一 cistella 库”。用户永远只需要打开、创建和管理一个当前库；文献、PDF 资产、笔记、标注、阅读会话、来源数据、导入批次、全文索引、系统记录等都作为这个库内部的混合数据存在。

底层继续以 tree-space / cistella-workspace 为基础：一个 Workspace Tree 是统一聚合根，各业务数据以子树、Named Block、派生缓存或兼容层方式挂载。某类数据是否存在，只表示该子树或 block 是否有内容，不再形成另一个用户可见的“库”。

## 2. 背景与问题

当前项目处在 legacy Vault 与 tree-space Workspace 并存的过渡阶段，前端因此出现多套“库”语义：

- `Vault`、`Library`、`Workspace`、`当前库`、`文献库` 在用户界面与代码中混用。
- Source 导入流程仍有“来源目录 / 输出目录 / 构建库”语义，容易让用户误以为 Source 分析拥有另一套库。
- Reading、Notes、Search、VaultPage 的资产中心都依赖同一个当前库，但页面文案没有稳定表达这种从属关系。
- 后端已经完成 tree-space 架构线最小闭环，但大量业务命令仍以 legacy `Vault` 作为运行入口。
- 前端侧边栏有“文献库 / 阅读 / 笔记 / 检索 / 来源分析 / 设置”等页面，但用户很难判断这些页面是不同库，还是同一个库的不同视图。

本工单的核心不是新增一个新库，而是取消多库心智：所有功能都围绕当前 cistella 库展开。

## 3. 单库化原则

### 3.1 用户心智

用户只需要理解一个对象：**cistella 库**。

用户路径应表达为：

1. 打开或新建一个 cistella 库。
2. 在这个库里导入文献、收纳 PDF、阅读、写笔记、检索和分析来源数据。
3. 复制、备份或迁移这个库时，库内可携带数据跟随库一起走；外部链接则明确提示“不随库复制”。

### 3.2 产品术语

| 层级 | 推荐术语 | 英文 | 说明 |
|---|---|---|---|
| 用户可见根对象 | 库 / cistella 库 / 当前库 | Library / current library | 唯一用户可见的持久对象 |
| 技术聚合根 | Workspace | Workspace | tree-space 上的聚合树，不作为普通用户主术语 |
| 历史兼容对象 | Vault | Legacy Vault / internal vault | 旧格式和过渡实现词，新增 UI 不主动暴露 |
| 业务内容 | 文献、资产、笔记、标注、来源数据、索引 | Literature, assets, notes, annotations, sources, index | 当前库内部的数据域 |

### 3.3 数据归属

所有业务数据都属于当前库：

| 数据域 | 归属 | 是否用户可见为“库” |
|---|---|---|
| 文献条目 | 当前库的 literature 域 | 否 |
| PDF / 附件资产 | 当前库的 assets 域 | 否 |
| 笔记与标注 | 当前库的 literature/writing/assets 相关域 | 否 |
| 阅读会话 | 当前库的 literature/assets 相关域 | 否 |
| Source 来源数据 | 当前库的 analysis/imports 域 | 否 |
| 导入批次与回滚记录 | 当前库的 imports/system 域 | 否 |
| 全文索引 | 当前库的 cache 域 | 否，属于可重建缓存 |
| 应用运行目录 | app directories | 否，是应用级运行配置，不是用户库 |

## 4. A/B/C 决策

### A 层：方向与范围

- 产品层用户可见对象只有一个：**cistella 库**。
- `Vault` 降级为历史兼容/内部实现词，不再作为新增用户界面的主术语。
- `Workspace` 是技术聚合根，不作为普通用户必须理解的概念。
- Source、Reading、Notes、Search、Settings 都是当前库的不同工作面，不是不同库。
- 导入流程只表达“导入到当前库”，不再要求用户理解“输出库”。
- tree-space 是底层统一混合库能力；前端仍不暴露 bucket、block、ref、tree-space path 等内部细节。

### B 层：设计取舍

- UI 术语优先统一为“库 / cistella 库”，英文统一为 `Library`。
- 后端逐步引入面向产品的 `Library`/`Workspace` façade，允许旧 `Vault` 类型作为过渡适配器继续存在。
- 单库内部的数据域沿用 `WorkspaceKind`：`literature`、`references`、`writing`、`assets`、`analysis`、`imports`、`system`、`cache`。
- 笔记、标注、阅读会话优先归入文献/资产相关子树，不急于为每个前端页面新增底层 kind。
- 迁移采用分阶段改造，不做一次性大爆炸重写。
- 前端先改用户可见文案和流程，再逐步重命名内部 React props/hook；Rust 类型可在 façade 层先引入兼容别名。

### C 层：实现约束

- 前端新增或调整文案时必须避免用户可见的 `Vault`/`Workspace` 混用。
- 现有命令和类型可保留兼容别名，但新增接口应优先使用 `library` 或产品化命名。
- 当前库状态应在 App 层统一维护，页面只消费当前库上下文，不自行创造新的“库路径”语义。
- 导入页面只能要求用户选择“来源”，目标默认是当前库；若当前无库，应引导用户先新建/打开库。
- 修改前端后必须执行构建并同步 `bin_test/cistella-frontend/`。
- 修改构建、打包或 bin_test 机制时必须同步更新 `AGENTS.md`。

## 5. 页面职责边界

| 当前页面 | 单库化后用户理解 | 主要数据域 | 调整重点 |
|---|---|---|---|
| VaultPage | 库管理 / 当前库 | system、imports、assets、overview | 页面命名从 Vault 心智转向 Library；导入改为“导入到当前库” |
| ReadingPage | 当前库里的文献与阅读 | literature、assets、reading sessions | 强调“当前库中的文献”；PDF 是条目的资产，不是另一个库 |
| NotesPage | 当前库里的笔记与标注 | notes、annotations、literature、assets | 笔记按文献组织，标注引用库内资产 |
| SearchPage | 搜索当前库 | cache、literature、assets | 索引是当前库的可重建缓存 |
| SourcePage | 当前库里的来源分析 | analysis、imports、sources | Source 是数据域，不是独立 Source 库 |
| SettingsPage | 应用设置与当前库运行方式 | app directories、system | 区分应用级目录和当前库目录 |
| Sidebar/CommandPalette | 进入当前库的不同工作面 | 路由层 | 避免暗示多个库；搜索双归属可保留但文案需清晰 |

## 6. 工单范围

### 包含

- 盘点并统一前端所有库相关术语与页面职责。
- 设计“当前 cistella 库”的产品模型、DTO 边界和命令命名策略。
- 调整 Vault/Workspace/Library 的分层关系说明。
- 规划 legacy Vault 到单库 Workspace 的迁移与兼容路径。
- 明确各页面映射到统一库内部哪些数据域。
- 对导入、最近库、资产外链、portable/installed 模式给出单库化解释。

### 不包含

- 不重写 tree-space 底层协议。
- 不在本工单一次性完成所有历史数据格式迁移。
- 不取消现有 legacy Vault 的读取、备份和迁移能力。
- 不把 tree-space 内部概念直接呈现给前端用户。
- 不把“单库化”理解成必须把库做成单个物理文件；目录型 Workspace 仍然符合单库产品心智。

## 7. 后端演进方向

### 7.1 当前状态

现有主业务命令大量通过 `Vault::open_any`、`vault_context`、`connect_vault` 等 legacy 名称运行。`cistella-workspace` 已提供 `WorkspaceHandle`、`WorkspaceContract`、legacy migration 等能力，但还没有成为所有业务命令的统一产品 façade。

### 7.2 目标方向

后端调用链逐步收敛为：

```text
Tauri commands
  ↓
cistella-workspace / Library façade
  ↓
cistella-tree-space registered blocks
  ↓
tree-space
```

legacy 兼容链保留为：

```text
legacy Vault input
  ↓
inspect / migrate / read-only compatibility
  ↓
current cistella Library / Workspace
```

### 7.3 最小可行 façade

本工单优先考虑以下 façade，不要求一次性替换全部旧命令：

- `open_library` / `connect_library`：用户语义的打开当前库入口。
- `library_context`：返回当前库摘要、数据域状态、legacy 状态、portable 状态。
- `library_contract`：在现有 `workspace_contract` 基础上提供产品化命名或兼容别名。
- `import_to_library`：把来源数据导入当前库，而不是导入到用户选择的“输出库”。
- `legacy_vault_*`：保留 legacy 兼容命名，避免与当前库混淆。

## 8. 前端演进方向

### 8.1 术语优先级

前端用户可见文案使用优先级：

1. 中文：`库`、`当前库`、`cistella 库`
2. 英文：`Library`、`current library`
3. 仅兼容/诊断场景：`Legacy Vault`
4. 禁止普通页面新增：裸露的 `Workspace`、`tree-space`、`bucket`、`block`、`ref`

### 8.2 首批改造点

- `dict.ts`：统一 `vaultTitle`、`vaultDesc`、`chooseVault`、`currentVault`、`assetsInVault` 等用户文案。
- `workspaceNavigation.ts`：确认侧边栏“文献库 / Library”是否应命名为“库管理 / Library”。
- `VaultPage.tsx`：把“选择输出目录 / 构建库”改成“选择/创建当前库 / 导入到当前库”的流程表达。
- `ReadingPage.tsx`：文案强调“当前库中的文献”。
- `SourcePage.tsx`：文案强调“当前库的来源数据/分析”。
- `SearchPage.tsx`：文案强调“当前库索引”，说明索引是可重建缓存。
- `SettingsPage.tsx`：明确 app directory 与 library directory 的区别。

## 9. 验收标准

### 9.1 设计验收

- 有一份明确的术语表，说明 `库 / Library / Workspace / Vault / Source / Asset` 的边界。
- 有一份页面映射表，说明每个前端页面对应当前库内部哪个数据域。
- 有后端 façade 迁移策略，说明哪些旧命令保留兼容，哪些新增命令采用 `library` 命名。

### 9.2 前端验收

- 普通用户可见 UI 不再混用 `Vault`、`Workspace`、`Library` 三套根对象术语。
- 导入流程不再制造“另一个输出库”的心智。
- 最近库、当前库、库内资产、外部链接的关系可被用户理解。
- 前端构建通过，并同步 `bin_test/cistella-frontend/`。

### 9.3 后端验收

- 新增或调整的 façade 不暴露 tree-space 内部细节。
- legacy Vault 兼容能力不被破坏。
- Rust 检查通过。

## 10. 预期结果

- 用户只需要理解“打开一个 cistella 库，然后在其中阅读、管理、检索、分析和写笔记”。
- 前端导航与页面文案不再制造多个“库”的错觉。
- 后端具备清晰的单库 façade 演进路线。
- legacy Vault 被明确为兼容输入，而不是未来产品主模型。
