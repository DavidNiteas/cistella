本工单的设计目标与范围边界已经由用户原始请求明确：参考 `E:/dev_repos/LCMSQueueMaker` 的 `bin_test/` 目录机制、标准编译入口机制、测试编译机制（无需内嵌前端即可测试），对 cistella 的编译与入口进行易用改造。

- 由于 cistella 桌面应用目前未完全前后端分离，且 `cistella-desktop` 的 `lib.rs` 承载了大量与 Tauri 强耦合的命令处理逻辑，本工单需要进行设计上的调整，将**命令业务逻辑**与**Tauri 命令转发层**分离。
- 本工单不承诺将 cistella 改造成完全前后端分离架构，也不新增产品级 CLI；目标是让 Rust 后端逻辑的编译、测试、预览更顺畅。
- cistella-core 保持纯 Rust；cistella-desktop 通过重构使命令逻辑可在无 Tauri runtime 环境下测试。

│   ├── openalex-analysis-core/             # 纯 Rust 核心库

│       │   ├── Cargo.toml                  # [lib] + [[bin]] cistella

│       │   │   ├── lib.rs   (74 KB)        # 全部 Tauri 命令实现
│       │   │   └── main.rs                 # 仅调用 cistella_desktop_lib::run()

### 2.2 关键问题

| 问题 | 位置 | 影响 |
|---|---|---|
| `lib.rs` 单体化 | `crates/openalex-analysis-studio/src-tauri/src/lib.rs`（74 KB） | 所有 Tauri 命令与业务逻辑挤在一个文件，难以单元测试和复用 |

## 3. 参考方案：LCMSQueueMaker 的关键机制

### 3.1 `bin_test/` 目录

`LCMSQueueMaker/bin_test/` 是**预构建产物目录**，存放可直接运行的 Windows artifacts：
- `lcms-queue-make.exe`（CLI）
- `lcms-queue-gui.exe`（Tauri GUI）
- `lcms_queue_py-*.whl`（PyO3 扩展）
- `.lcms_env/.venv/`（运行时 Python 环境）

由 `pixi run build-release` → `LCMSQueueMaker-Studio/build-release.sh` 统一生成，最后一步复制产物到 `bin_test/`。

### 3.2 标准编译入口

`LCMSQueueMaker-Studio/Cargo.toml` 采用 `[lib]` + 多 `[[bin]]`：
- `[lib]`：`lcms_queue_make`，path `src/lib.rs`
- `[[bin]]`：`lcms-queue-make`，path `src/main.rs`
- `[[bin]]`：`lcms-queue-gui`，path `src-tauri/main.rs`

命令示例：
- `cargo build --release --bin lcms-queue-make`
- `cargo build --release --bin lcms-queue-gui`
- `cd LCMSQueueMaker-Studio && cargo test --lib`

### 3.3 测试编译机制（无需内嵌前端）

- 算法核心 `lcms-queue-algorithms` 是独立 workspace，可 `cargo test -p lcms-queue-algorithms`
- `LCMSQueueMaker-Studio/src/lib.rs` 不包含 Tauri/前端代码，`cargo test --lib` 只测试库逻辑
- 前端 `src-ui/` 是独立 npm 项目，仅 GUI 构建时通过 `tauri.conf.json` 引用 `src-ui/dist`
- 因此 Rust 单元测试和 CI 不必安装 Node 依赖

### 3.4 对 cistella 的借鉴点

1. **命令业务逻辑与 Tauri 转发层分离**：把命令实现抽到可独立测试的模块。
2. **多 bin 入口**：GUI bin + headless/CLI bin，便于测试和脚本调用。
3. **`bin_test/` 预构建目录**：统一存放可执行产物，便于 QA 和分发预览。
4. **统一发布脚本**：一条命令完成前端构建、Rust 构建、产物汇总、打包。
5. **测试解耦**：`cargo test --lib` 不触发前端构建。

## 4. 新设计方案

### 4.1 架构调整

在保持 cistella 桌面应用为唯一产品入口的前提下，对 `cistella-desktop` crate 做如下重构：

```text
crates/openalex-analysis-studio/src-tauri/src/
├── main.rs                          # GUI 入口：调用 app::run()
├── bin/
│   └── headless.rs                  # headless CLI 入口（新增）
├── app/
│   ├── mod.rs                       # Tauri app 初始化、状态管理、命令注册
│   ├── commands.rs                  # Tauri command handler（薄转发层）
│   └── state.rs                     # Tauri State 定义
└── commands/                        # 业务命令实现（新增/拆分自 lib.rs）
    ├── mod.rs
    ├── vault.rs                     # Vault 连接、最近库、迁移等
    ├── literature.rs                # 文献条目 CRUD、导入、远程解析
    ├── reading.rs                   # 阅读会话
    ├── search.rs                    # 本地全文检索
    ├── source.rs                    # Source 分析
    ├── notes.rs                     # 笔记与标注
    └── settings.rs                  # 设置、备份恢复
```

关键变化：
- `commands/` 下的每个模块只包含**纯函数/结构体方法**，接收 `AppContext`（或具体上下文）参数，返回 `Result<T, Error>`。
- `app/commands.rs` 中的 `#[tauri::command]` 函数只负责：
  1. 从 Tauri State 中组装 `AppContext`。
  2. 调用 `commands::xxx::handler(...)`。
  3. 将结果返回给前端。
- `bin/headless.rs` 通过 clap 解析参数，直接构造 `AppContext` 并调用 `commands/` 中的函数。

### 4.2 `AppContext` 设计

```rust
pub struct AppContext {
    pub vault_path: Option<PathBuf>,
    pub app_dirs: AppDirectories,
    pub config: AppConfig,
    // 其他跨命令共享的上下文
}

impl AppContext {
    pub fn new(app_dirs: AppDirectories, config: AppConfig) -> Self;
    pub fn connect_vault(&mut self, path: &Path) -> Result<VaultContext, Error>;
    // ...
}
```

- `AppContext` 不包含任何 Tauri 类型，可在 headless binary 和测试中直接构造。
- Tauri State 中保存 `Mutex<AppContext>` 或 `Arc<RwLock<AppContext>>`。

### 4.3 多 bin 入口

`crates/openalex-analysis-studio/src-tauri/Cargo.toml`：

```toml
[lib]
name = "cistella_desktop_lib"
crate-type = ["staticlib", "cdylib", "rlib"]

[[bin]]
name = "cistella"
path = "src/main.rs"

[[bin]]
name = "cistella-headless"
path = "src/bin/headless.rs"
```

- `cistella`：Tauri GUI 入口（现有）。
- `cistella-headless`：无前端 CLI/test 入口（新增）。

### 4.4 headless CLI 设计

headless binary 不是产品级 CLI，而是**开发/测试/脚本工具**。示例命令：

```bash
# 连接库并输出库概览
cistella-headless vault open --path "E:\vaults\my-lib"

# 查询 Source 排行
cistella-headless source rank --metric h_index --type journal --limit 10

# 执行本地搜索
cistella-headless search --query "machine learning" --scope all

# 列出文献条目
cistella-headless literature list --status reading

# 运行健康检查
cistella-headless doctor
```

实现方式：
- 使用 `clap` 做参数解析（workspace 中已有，但当前未在 desktop crate 使用）。
- 每个 subcommand 调用 `commands::xxx` 中的函数。
- 输出使用 `serde_json` 或人类可读表格，默认 JSON，便于脚本解析。

### 4.5 `bin_test/` 目录

在项目根创建 `bin_test/`：

```text
bin_test/
├── cistella.exe                  # GUI 可执行文件
├── cistella-headless.exe         # headless CLI 可执行文件
├── cistella-portable/            # 便携模式 marker 目录（空目录）
└── README.txt                    # 使用说明
```

- `bin_test/` 不纳入 git 版本控制（加入 `.gitignore`）。
- 由新的发布脚本 `scripts/build-release.js`（或 `.sh` / `.ps1`）生成。
- 作为预构建产物目录，方便 QA 直接运行和冒烟测试。

### 4.6 统一发布脚本

新建或改造发布脚本，标准流程：

```text
1. pnpm build                      # 构建前端到 dist/
2. cargo build --release --bin cistella
3. cargo build --release --bin cistella-headless
4. 复制 exe 到 bin_test/
5. node scripts/make-portable.js   # 打包 portable zip
```

脚本位置建议：
- `crates/openalex-analysis-studio/scripts/build-release.js`：跨平台 Node 脚本，调用 pnpm 和 cargo。
- 或 `scripts/build-release.ps1` + `scripts/build-release.sh`：原生脚本，不依赖 Node。

本工单先实现 Node 脚本，与现有 `make-portable.js` 风格保持一致；后续可考虑补充 PowerShell/Bash 原生脚本。

### 4.7 测试编译机制

改造后测试命令：

```bash
# 核心算法/数据模型测试（纯 Rust，无需前端）
cargo test -p cistella-core --lib

# 桌面库命令转发层测试（无需前端构建）
cargo test -p cistella-desktop --lib

# headless binary 测试（无需前端）
cargo test --bin cistella-headless

# 端到端：使用 headless CLI 做冒烟测试
cargo run --release --bin cistella-headless -- doctor
```

注意：
- `cargo test -p cistella-desktop --lib` 只编译 lib，不执行 `tauri.conf.json` 的 `beforeBuildCommand`。
- 业务逻辑集中在 `commands/` 模块，单元测试写在该模块的 `#[cfg(test)]` 中。
- 需要 Tauri runtime 的测试（如命令注册）保留在 `app/commands.rs` 的测试中。

### 4.8 现有 `lib.rs` 拆分策略

由于 `lib.rs` 当前 74 KB，一次性完全拆分风险高，采用渐进式拆分：

1. **P0（本工单）**：
   - 创建 `commands/` 目录框架。
   - 把 `lib.rs` 中的类型定义和辅助函数抽到 `types.rs` / `utils.rs`。
   - 把命令按工作区迁移到 `commands/{vault,literature,reading,search,source,notes,settings}.rs`。
   - 保留 Tauri command handler 在 `app/commands.rs`（从 lib.rs 改名或拆分）。
   - 新增 `bin/headless.rs`。

2. **P1（后续可选）**：
   - 进一步把 `commands/` 中重复的 `invoke` 调用封装为 `core_bridge` 模块。
   - 把 `commands/` 拆成独立 crate（如果需要被多个宿主复用）。

## 5. 不改动范围

- 不修改 `cistella-core` 的数据模型、存储布局、API 契约。
- 不修改前端 React/Vite 代码（除非需要调整构建脚本路径）。
- 不新增产品级 CLI；`cistella-headless` 仅用于开发、测试、脚本。
- 不修改 `tauri.conf.json` 中的产品名称、版本、窗口配置。
- 不引入新的构建工具（如 pixi）；继续使用 pnpm + cargo。

## 6. 关键术语

- **`bin_test/`**：预构建产物目录，存放可直接运行的可执行文件。
- **`cistella-headless`**：无前端 CLI/test binary。
- **`commands/`**：Tauri 命令业务逻辑模块，与 Tauri runtime 解耦。
- **`AppContext`**：跨命令共享的纯 Rust 上下文，可在 Tauri 和 headless 环境中构造。
- **`cargo test --lib`**：只测试 Rust lib，不构建前端、不运行 Tauri。
