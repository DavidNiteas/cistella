: 编译与入口易用改造

## 1. 总体策略

采用「先建立多 bin 入口与 bin_test 目录 → 再拆分 lib.rs 中的命令业务逻辑 → 最后统一发布脚本」的三阶段策略。每一阶段都保持 `pnpm build` 和 `cargo check -p cistella-desktop` 通过，避免一次性大拆带来的回归风险。

## 2. 里程碑表

| 里程碑 | 内容/交付物 | 关闭标准 | 验收命令 | 依赖 |
|---|---|---|---|---|
| M1 | 多 bin 入口 + `bin_test/` 目录 + 统一发布脚本 | 存在 `cistella-headless` bin；`bin_test/` 可生成；统一脚本可用 | `cargo check -p cistella-desktop`、`cargo build --bin cistella-headless`、脚本复制产物验证 | 无 |
| M2 | 拆分 `lib.rs`：命令业务逻辑下沉到 `commands/`，Tauri handler 变薄 | `lib.rs` 行数显著下降；`commands/` 模块可在 headless 中调用；所有原 Tauri 命令仍可用 | `pnpm build`、`cargo check -p cistella-desktop`、`cargo test -p cistella-desktop --lib`、`cargo test --bin cistella-headless` | M1 |
| M3 | headless CLI 功能补齐 + 冒烟测试 + 文档 | `cistella-headless` 支持 vault/source/search/literature 等子命令；文档更新 | `cargo run --bin cistella-headless -- doctor`、统一脚本全量跑通、前端功能回归 | M2 |

## 5. 风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| `lib.rs` 拆分引入命令行为回归 | 前端功能异常 | 每批次后运行 `cargo check` + `pnpm build`；M3 做功能回归 |
| Tauri State 与 `AppContext` 并发访问问题 | 数据竞争或死锁 | 使用 `Arc<RwLock<AppContext>>`；命令中短暂持有锁 |
| `clap` 增加 desktop crate 依赖体积 | release 产物变大 | `clap` 只在 `cistella-headless` bin 使用；用 feature gate 控制 |
| headless binary 误被当作产品 CLI | 用户期望管理 | 文档明确说明 headless 仅用于开发/测试/脚本 |
| 统一脚本在 Windows 外不兼容 | Linux/macOS 开发者无法使用 | M1 先实现 Node 脚本；后续可补 PowerShell/Bash 原生脚本 |

## 6. 施工协议

- **先文档后实现**：任何架构偏离必须先更新本工单 `01-目标与设计.md`，并在 `03-开发状态.md` 登记，再动代码。
- **禁止双写**：状态细节只写本工单 `03-开发状态.md`；全局 `开发状态.md` 仅做导航索引。
- **偏离申请**：C 层实现细节偏离按默认规则裁定；触及 B 层设计或 A 层方向时升级经理。
- **分阶段闭合**：M1/M2/M3 各自独立验收，不累积到最后一刻。
