## 1. P-IO 磁盘模型（P-0 核心决策 + P-IO-1 对象规范，2026-08-22 定稿）

> 本节为 P-IO 批次的完整规范核心：§1.1–§1.7 为 P-0 决策（P-IO-1 修订处已注明），§1.9 为 P-IO-1 落笔的对象规范细化。剩余开放议题见 §1.8。

### 1.1 库的磁盘单元

一个「库」= 树实例 + 桶（归档工单 §4.1）。磁盘单元 = **一个 commit 链**（沿用 v4 ParquetDir content-addressed commit-tree）：每次提交产生 commit 对象，携带 TB 根树指针；`committed` 文件仍为唯一可见性点（v4 语义不变）。

### 1.2 块对象：envelope 整体作 blob

桶的存储单元是 envelope（kind + payload），磁盘 blob = **envelope 全字节**：

- 自描述随行（kind/name 信息不丢），弱解码能力与内存语义一致；
- 内存语义 = 磁盘语义：桶重开 = envelope 集合重装，无拼装步骤；
- 注册块（envelope v2 帧）天然同规则。

### 1.3 blob 地址：严格铁律（P-IO-1 修订：manifest 取消）

对齐 v4 双哈希铁律（存储地址用独立全内容哈希，绝不用语义 digest）：

- **块 blob 地址** = envelope 全字节的存储层全内容哈希；
- **语义身份**（`RefId`，`tb-block-*` 域）不参与物理寻址；树侧同理（`TreeId` 不参与寻址，树字节 blob 地址 = 树字节全内容哈希）。

> **P-IO-1 修订（2026-08-22）**：P-0 定稿的「bucket manifest 对象」（RefId↔地址全桶映射）**取消**，其职能由 §1.4 派生引用表吸收——引用表直接携带 blob 地址（GC 单跳）；重开时 RefId 从 envelope 自算（envelope 自描述，kind+payload 全在），无需任何映射对象。理由：manifest 的两个消费者（GC、重开）均被覆盖，独立对象徒增一个家族、一套 golden 与一跳间接。评估过的替代（RefId 即地址）维持弃选——地址哈希输入不含帧字节，按铁律字面属偏离；本工单铁律零例外。

### 1.4 树对象：单真相 + 派生引用表（P-IO-1 修订：新对象家族）

**canonical 树字节 blob 是树对象的唯一真相源**：

- **存储**：树实例的 canonical IPC 字节（归档工单 §5）存为 blob；地址 = 树字节全内容哈希（铁律树侧对应）；
- **commit 时派生**：从提交形态的树的 `leaf_refs` 生成** TB 引用表对象**（新对象家族，三列：xpath 规范字节 / `RefId` / blob 地址——详见 §1.9）。引用表是**派生数据**（性质对齐 ChunkStats：可重算、不参与身份、不构成第二真相源），服务三处——磁盘 GC 可达性（存储层只读引用表、零格式解释，v4 分层保持）、重开时 `XPathIndex` 的重建源、verify 三列互验（不解码树字节即可校验一致性）；
- **一致性可校验**：verify 扩展重算树字节 leaf_refs 与引用表比对（内容级检查）。

> **P-IO-1 修订（2026-08-22）**：P-0 定稿的「生成 v4 tree 对象条目（xpath→RefId）」修订为「新 TB 引用表对象家族」。代码事实依据：v4 tree 对象条目 = `(TableId: FSB16, content_hash: FSB16)`——TB xpath（变长规范字节）放不进 TableId 槽；v4 blob 通道为 `tables/{id}-{hash}.parquet`（parquet 编码）——envelope 原始二进制进不了该通道。TB 对象必须走新通道（§1.9）；v4 `tables/`、`trees/`、`commits/`、`metadata/` 通道与既有字节**完全不动**。
>
> 讨论中评估过的替代（单 blob + GC 解码树字节找 RefId）被弃选——IO 层解释模型层格式破坏 v4 分层；（条目表与树字节均为真相源的双冻结方案）被弃选——每 commit 双写且引入真相漂移风险。

### 1.5 commit 对象：v4 可选字段追加 + 旧读端降级

v4 commit 对象（单行 Arrow IPC batch：sequence / parent / tree_id / metadata_ref，golden 冻结）通过**追加列**携带 TB 根树指针（追加列形状见 §1.9；P-0 定稿的「manifest 引用」随 §1.3 修订取消）：

- 遵循 v4 追加式演进前向契约：旧读端按列索引读 0–3 不受追加列影响；旧数据字节不变；
- **旧读端降级（P-IO-1 定稿）**：TB commit 的 v4 `tree_id` 字段指向**规范空 v4 tree 对象**、`metadata_ref` 指向**规范空 metadata 快照**（两者内容恒定 → id 恒定 → 磁盘仅写一次）——旧读端打开 TB 目录看到「空表集」而非 corrupt；既有 v4 golden 不重冻结；新增对象形状进 P-IO golden 新清单（§1.9）。

### 1.6 ephemeral 落地（前向契约兑现）

归档工单 §3.5 三条语义的磁盘兑现（细节归 P-IO-5）：

1. **写盘剪枝**：commit 跳过 ephemeral 子树的块写入；被剪 xpath 记录进 commit（供 verify 与诊断；记录格式 P-IO-5 定）；
2. **读取尽力**：重开时 ephemeral 字段回默认值；旧提交窗口内可达数据可找回，找不到不报错；
3. **注记随行**：persistence 注记进 commit（不进 canonical 树字节——归档工单前向契约维持）。

> **P-IO-1 前置澄清（倾向记录，P-IO-5 裁定）**：**提交形态的树** = 剪枝后的形态——committed 树字节剥离 ephemeral 子树，TB 引用表（§1.4）从剥离形态派生 → 被剪块天然不可达、被 GC 自然回收；「读取尽力」的找回走历史 commit 链（v4 保留 committed epochs 语义）。

> **P-IO-5 裁定落地（2026-08-22）**：本节三条语义的磁盘兑现细节定稿于 §1.9.8（剪枝记录列 `tb_pruned`、image 层剪枝、读取尽力 Default 回填、GC 复用既有窗口、verify 剪枝一致性）。

### 1.7 接线与回补

- **TreeImage ↔ XPathIndex**：重开自 TB 引用表（或树字节）重建 `XPathIndex`；`TreeImage` 成为 v4 `TreeInstance` 的 TB 侧对应面，接线形状归 P-IO-4；

### 1.9 P-IO 对象规范（P-IO-1 定稿，2026-08-22）

> 本节冻结 TB 磁盘对象形状；任何变更 = 字节变 = 先修订本节并重冻结 golden。库句柄 API 形状（open/commit 入口类型、`TreeLibrary` 命名等）是**实现自由度**，选择记录进施工日志。

#### 1.9.1 目录布局（ParquetDir 扩展）

```text
<root>/
├── committed            # v4 唯一可见性点（不变）
├── commits/  {id}.ipc   # v4 commit 对象（不变；TB commit 追加列，见 1.9.5）
├── trees/    {id}.ipc   # v4 tree 对象（不变；TB commit 挂规范空对象）
├── tables/   …          # v4 blob 通道（不变，纯 v4 数据专用）
├── metadata/ …          # v4 metadata 快照（不变；TB commit 挂规范空快照）
├── tb-blocks/ {address}.bin   # 新通道：块 envelope blob（原始字节）
├── tb-trees/  {address}.ipc   # 新通道：canonical 树字节 blob（Arrow IPC）
└── tb-refs/   {address}.ipc   # 新通道：TB 引用表对象（Arrow IPC，见 1.9.4）
```

- 文件名 `{address}` = 16 字节地址的 hex（与 v4 `{digest}` Display 惯例一致）；
- 写入语义对齐 v4：目标已存在即跳过（内容寻址去重；存在性检查 = 文件名）；
- 旧读端对 TB 目录：`committed → commit（读列 0–3）→ 空 tree/空 metadata` → 「空表集」，无 corrupt。

#### 1.9.2 块 blob（tb-blocks/）

- 内容 = **envelope 全字节**（v1/v2 帧原样，含 kind/name/版本/长度）；
- **地址公式（P-IO-2 落定，2026-08-22）**：`block_blob_address = canonical_digest(b"tb-blob", [envelope_bytes])`（16B；语义 `RefId` 不参与，§1.3）。§1.9.2 原「全内容哈希」未定域标签——施工落定 b"tb-blob"，与 `RefId` 的 `tb-block-*` 域、树 blob 的 `tb-tree-blob` 域、引用表 `tb-refs` 域互相隔离；
- 重开：扫描 `tb-blobs` 下 `tb-blobs/` 文件名 `{address}.bin` → 每文件 `Envelope::decode` → `RefId = canonical_digest(kind.domain(), [payload])` 自算 → 装桶（RefId → envelope）。重开同时校验文件名地址 == `block_blob_address(文件字节)`（地址伪造即报错）。写入语义：目标已存在即跳过（内容寻址去重）。

#### 1.9.3 树 blob（tb-trees/）

- 内容 = 树实例 canonical IPC 字节（归档工单 §5 平面条目表）；
- **地址公式（P-IO-2 落定，2026-08-22）**：`tree_blob_address = canonical_digest(b"tb-tree-blob", [tree_bytes])`；`TreeId = canonical_digest(b"tb-tree", [bytes])` 与地址独立（铁律）。§1.9.3 原「树字节全内容哈希」未定域标签——施工落定为 b"tb-tree-blob"。

#### 1.9.4 TB 引用表对象（tb-refs/）

- 内容 = 单 RecordBatch 的 canonical IPC（复用 `encode_batch` + `canonicalize_null_slots` 管道），三列：

| 列 | Arrow 类型 | 语义 |
|---|---|---|
| `xpath` | Binary（non-null） | `canonical_xpath_bytes`（归档工单 §4.4.2 注入编码） |
| `ref_id` | FixedSizeBinary(16)（non-null） | 语义身份（`tb-block-*` 域） |
| `address` | FixedSizeBinary(16)（non-null） | `tb-blocks/` blob 地址 |

- **行序（canonical，MUST）**：按 `xpath` 规范字节升序——同一提交形态的树必得同一引用表字节（内容寻址去重稳定）；
- **派生规则**：提交形态的树的 `leaf_refs`（含去重：同一 RefId 多 xpath = 多行；同一 (xpath, RefId) 恒一行）⊕ 桶内 RefId → 地址解析；
- **地址公式（P-IO-2 落定，2026-08-22）**：`ref_table_address = canonical_digest(b"tb-refs", [ref_table_ipc_bytes])`。§1.9.4 原「引用表对象字节全内容哈希」未定域标签——施工落定为 b"tb-refs"；
- 消费者：GC（`address` 列，单跳）、`XPathIndex` 重建（`xpath`+`ref_id` 列）、verify（三列互验：blob at address 的 envelope 自算 RefId == `ref_id` 列；树字节重算 leaf_refs ≡ 引用表行集）。
- **弱意象与 xpath 语义（P-IO-3 澄清，2026-08-22）**：引用表 `xpath` 列 = 提交形态树（typed `leaf_refs` / `DynamicNode::leaf_refs`）产出的规范字节——String-keyed Map 块叶子取 `Step::Key` 语义（保证重开 `XPathIndex` 查询等价）。verify 的「树字节重算 leaf_refs」从弱意象（`TreeImage`）走结构遍历（Field/Index，chunk/view 叶子的位置语义与 typed/dynamic 一致）；因 canonical 平面条目表不编码「struct 字段 vs String Map 键」区分（§5.3 规则 3 类型擦除），**String-keyed Map 块叶子不在本里程碑 verify 字节级互验覆盖类**（golden 20 样本树不含该类叶子）——该限制已记录施工日志。

#### 1.9.5 commit 对象追加列（v4 单行 batch 扩展）

v4 既有四列（sequence: UInt64 / parent: FSB16 / tree_id: FSB16 / metadata_ref: Utf8）不变，**追加三列**（全 nullable）：

| 追加列 | Arrow 类型 | 语义 |
|---|---|---|
| `tb_root_tree_id` | FixedSizeBinary(16) | 根 `TreeId`（语义身份） |
| `tb_tree_blob` | FixedSizeBinary(16) | `tb-trees/` 树字节地址 |
| `tb_refs` | FixedSizeBinary(16) | `tb-refs/` 引用表地址 |

- **TB commit**：三列全部非空；v4 `tree_id` = 空 v4 tree 对象 id（恒定）；`metadata_ref` = 空 metadata 快照引用（恒定）；
- **纯 v4 commit**：三列全 null（旧写端行为不变，字节不变）；
- **第 4 追加列 `tb_pruned`（P-IO-5，§1.9.8）**：按追加式契约扩展（TB commit 7 列 → 8 列）；旧 7 列 TB commit 新读端按 `tb_pruned = null` 降级可读（无剪枝语义）；`tb_commit_id` 五 part 公式**不变**（`tb_pruned` 不入域，见 §1.9.8（b）5）。
- **TB commit 的 `commit_id`（P-IO-3 落定，2026-08-22）**：§1.9.5 原规范未定义 TB commit（追加列后）的 `commit_id` 派生。落定：`tb_commit_id = canonical_digest(b"commit", [sequence_le, parent, tb_root_tree_id, tb_tree_blob, tb_refs])`——v4 四列中的 `tree_id`/`metadata_ref` 为恒定空对象，不入域（与 §1.5「两个恒定」一致；v4 原始公式的四个 part 中前两个 `sequence`/`parent` 语义保留，空 tree_id/空 metadata_ref 直接以 TB 追加以偿避免碰撞）。纯 v4 commit 继续用原四 part 公式（`commit_id(sequence, parent, tree_id, metadata_ref)`），字节与 id 不变。
- **空 metadata 快照内容（P-IO-2 落定，2026-08-22）**：§1.9.1/§1.9.5 所述「规范空 metadata 快照」= `BootstrapImage::built_in()`（`special::empty_tables()` 九张零行特殊表 + 内置 manifest 种子）经 v4 `metadata_ref` 公式得到的恒定对象——旧读端可经其对 9 张特殊表正常自举（空注册表 → 空表集），非 corrupt。

#### 1.9.6 GC 扩展

- 可达集 = v4 既有遍历（commit 链 → v4 tree → `tables/` blob、`metadata/`）**∪ TB 遍历**（commit 追加列 → `tb-trees/` 树字节地址 + `tb-refs/` 引用表地址 → `tb-blocks/` blob + 引用表/树 blob 自身）；
- sweep 扩展到 `tb-blocks/`、`tb-trees/`、`tb-refs/` 三目录；`keep_from_sequence` 窗口语义对 TB 对象同样适用；
- **GC 不解码树字节**（零格式解释维持）：块可达性只经 `tb-refs`；
- **剪枝可达性（P-IO-5 定稿）**：被剪块随引用表从剪枝形态派生即不可达（同 commit 即回收）；ephemeral「读取尽力」的历史找回走 commit 链，受 `keep_from_sequence` 窗口约束——无专属窗口。

#### 1.9.7 golden 新清单（P-IO 冻结义务）

16. 空 v4 tree 对象 id + 空 metadata 快照引用（降级对象，恒定值）；
17. 块 blob 地址 golden（样本 envelope 的 `{address}` 与文件字节）；
18. 树 blob 地址 golden + 引用表对象字节 golden（样本树：三列 + 行序）；
19. TB commit 对象字节 golden（含追加列与 v4 四列合体的完整单行 batch）；
20. 重开等价性（行为断言）：构造 → 落盘 → 重开（树+桶+索引） ≡ 内存原象（TreeImage 相等、桶 envelope 集相等、`XPathIndex` 查询等价）；
21. 旧读端降级断言：v4 打开面对 TB 目录返回空库、不报错；纯 v4 目录在新读端下行为不变（全量 v4 回归即证）。

**负向必含**：blob 内容哈希 ≠ 文件名（地址伪造）、引用表 `address` 悬挂（指向缺失 blob）、`ref_id` ≠ envelope 自算（身份伪造）、引用表行序乱、commit 追加列类型错/半空（TB commit 缺列）、树 blob 截断/坏 magic、引用表 schema 不符、GC 后可达集完整性（被引用 blob 不被回收、孤儿被回收）。

#### 1.9.8 P-IO-5 对象规范：ephemeral 落盘 + derive 回补（2026-08-22 定稿）

> 本节冻结 ephemeral 剪枝/读取尽力/注记随行的磁盘契约与 derive 标注契约。API 形状（库句柄入口类型、`TreeNodeMeta` 暴露前缀集的方式、剪枝函数签名）是**实现自由度**，选择记录进施工日志。深层「树上下文 schema 校验」（Table 列 schema 期望 / Sequence 元素类型 / Kv 键值类型 / Blob 内容类型标注）**不在本里程碑**，后置小里程碑 P-IO-5b。

**（a）ephemeral 标注（derive）**

1. **标注语法**：字段属性 `#[tree_space(ephemeral)]`（helper attribute；`TreeNode`/`TreeCodec` 两 derive 均声明 `attributes(tree_space)`）。
2. **标注面**：仅可标注「节点字段（子树，任意基数）」或「容器字段（`Option`/`Vec`/`BTreeMap`）」；**Single 基数的叶子字段（Block/Inline）禁止标注**——derive 编译期报错。ephemeral 是「子树/容器」IO 策略，裸叶子无自然空形态。
3. **元数据**：进 `FieldMeta.ephemeral: bool`（模板元数据；不进 canonical 树字节；标记翻转不改 `TreeId`——归档 §3.5 前向契约）。
4. **默认值（MUST）**：ephemeral 字段重开 = 字段类型 `Default::default()`——节点递归 Default、`Option`→`None`、`Vec`/`BTreeMap`→空。derive 生成 `Default::default()` 回填；字段类型无 `Default` 即编译报错（编译期契约，非运行期 SchemaMismatch）。
5. **前缀集**：ephemeral prefixes = 模板 DAG 上所有 ephemeral 字段的 xpath 前缀（单调性：ephemeral 前缀覆盖下的子路径不重复登记，不深入 ephemeral 子树）；由 `TreeNodeMeta` 暴露（API 形状实现自由）。`DynamicNode::Persistence.mark_ephemeral` 的运行时前缀与类型标注前缀**合并去重**，构成提交实例的完整 ephemeral 前缀集。**可达性边界（2026-08-22 施工核实）**：容器元素类型内部声明的 ephemeral 字段，其 DAG 路径不含运行时下标（如 `Vec<Run>` 里 `Run` 的 `#[tree_space(ephemeral)] tmp` → 前缀 `/runs/tmp`），不会命中真实实例路径（`/runs/0/tmp`）→ 该组合**不剪枝**（无假阳性）；本里程碑的剪枝单元是「固定深度链上的字段」与「容器字段（Option/Vec/BTreeMap）整体」，后者含 ChunkGroup/View 整字段。

**（b）写盘剪枝（commit）**

1. **剪枝落点（image 层过滤）**：commit 时取实例全量 `ImageField`（`EncodeTree::tree_children()`，A-2 冻结接口不改）→ 按 ephemeral 前缀集过滤（xpath 落在任一前缀下即剔除该字段及其全部子树）→ IPC 编码得**剪枝树字节**；`leaf_refs` 从剪枝形态重新推导（被剪叶子自然消失）。
2. **块写入跳过**：被剪子树内的块叶子不写 `tb-blocks/`、不进引用表。
3. **引用表**：从剪枝形态派生（§1.9.4 派生规则不变）——被剪块同 commit 即不可达。
4. **剪枝记录列**：commit 追加**第 4 列 `tb_pruned: List<Binary>`**（nullable）——元素 = 被剪 maximal 前缀的 `canonical_xpath_bytes`；无剪枝 = `null`（空 List 表「启用但本次无剪枝」，与 null 语义区分）；纯 v4 commit = `null`。
5. **commit_id 不变**：`tb_commit_id` 五 part 公式（§1.9.5）**不变**——`tb_pruned` 不入域（sequence 已保证 commit 唯一；`tb_pruned` 是 `tb_tree_blob`/`tb_refs` 的推导冗余，与「两个恒定空对象不入域」的冗余排除精神一致）。

**（c）读取尽力**

1. **重开**：`project()` 重建时 ephemeral 字段 = `Default::default()`（不报 missing/不报 SchemaMismatch）；非 ephemeral 字段的缺失校验不变（既有 a2_2 负向）。
2. **找回**：走历史 commit 链（受 `keep_from_sequence` 窗口）；schema-ephemeral（类型标注）字段恒无历史数据 → 恒默认值，不报错（「找不到不报错」的 typed 兑现）；运行时标记字段可向前找（标记前的 commit 有数据）。

**（d）GC（复用既有窗口，确定性落笔）**

被剪块随引用表派生即不可达（同 commit 回收）；历史找回受 §1.9.6 既有 `keep_from_sequence` 窗口约束，无新机制（已回写 §1.9.6）。

**（e）verify 扩展（剪枝一致性）**

1. 既有三列互验 + `leaf_refs ≡ 引用表` 对剪枝形态成立（被剪块不出现，天然满足）。
2. **新增剪枝一致性**：`tb_pruned` 前缀集与引用表 xpath 列互斥——任何 `tb_pruned` 前缀下的 xpath 不得出现在引用表（被剪干净）；`tb_pruned` 非 null 且非空时，剪枝树字节重算的 `leaf_refs` 不得含该前缀下的叶子。
3. `tb_pruned` 供诊断（记录被剪集，可回放）。

**（f）注记随行**

persistence 注记进 commit 的承载 = `tb_pruned` 列（被剪前缀集）；canonical 树字节不含注记（归档 §3.5 不进 canonical）；`TreeId` 不变。

**（g）golden 新清单（P-IO-5 冻结义务，续 16–21）**

22. 剪枝树字节 golden（样本 ephemeral 树：剪枝形态 canonical 字节）；
23. 剪枝引用表 golden（被剪块不在其中）；
24. TB commit 含 `tb_pruned` 列字节 golden（8 列完整单行 batch）；
25. 读取尽力行为 golden（重开 ephemeral 字段 = 默认值；非 ephemeral 缺失仍报错）。

**负向必含**：ephemeral 标注在 Single 叶子上 derive 编译报错（derive 单测）；ephemeral 字段类型无 `Default` 编译报错（derive 单测）；verify 剪枝一致性（`tb_pruned` 前缀与引用表冲突 → 报错）；`tb_pruned` 列类型错 / 半空（8 列 commit 缺列）→ 报错；旧 7 列 TB commit 新读端降级可读（`tb_pruned` 视为 null，无剪枝语义）。

**（h）golden 19 重冻结（追加式契约的预期演化）**

`tb_pruned` 追加列使 TB commit 从 7 列 → 8 列，golden 19（7 列 commit 字节）随**重冻结为 8 列字节**（该样本无剪枝 → `tb_pruned = null`），**commit_id 值不变**（五 part 公式不变）。属 §1.9.5「追加式契约扩展」的预期演化，非 v4 golden 变更。

#### 1.10.2 对下游契约面（解冻前提：契约不再漂移）

对下游的契约 = **主数据路径 + view 组织 + 桶存整表**，全部已由 P-IO-2..5 落地：

| 契约 | 形态 | 状态 |
|---|---|---|
| 桶存块/表 | `Bucket`（content-addressed）；`ArrowTable` 块 = 整张表（polars 式，下游把整表塞进桶） | ✅ 归档 / P-IO-2 |

#### 1.10.5 sync / 并发写：解冻后横向能力（可行性落笔 + 批次登记）

**现状（2026-08-22 核实）**：v4 有 `sync::synchronize`（`Library` 面）与 service M12 五动词（受理序号/全局屏障/wait）；树+桶 `TbLibrary` **无 sync**，并发写仅 `metadata_lock` 的 `FileLock::try_exclusive`（跨进程**非阻塞**独占锁，冲突即 `LockUnavailable`，无 barrier/受理/wait）。

**可行性论证（content-addressed 不可变追加模型）**——两项能力都被模型**退化为单调幂等操作**，比 v4 更简单：

1. **同步 = 内容寻址对象传输（git fetch 式）**：
   - 源/目标均按内容寻址，同步 = 把可达对象（块 blob + 树字节 + 引用表 + commit 链）拷到目标；
   - 幂等（`exists → skip`）、可增量（只传缺失对象）、天然去重；
   - 无需锁目标全表空间（对象内容独立），v4 的「表空间逻辑状态同步」简化为「不可变对象集传输」。
2. **并发写 = 单点指针 CAS**：
   - 写块/树/引用表：`atomic_write_bytes` + `exists → skip`，多进程并行写同一 blob 不冲突；
   - 唯一竞争点 = `write_committed`（committed 头指针推新序列）——一处 CAS；
   - v4 表空间「原地可变表」要锁整个表空间 + reader/writer 可见性；树+桶「追加新树 + 换指针」，旧树永不变；
   - **推论**：v4 M12 的「全局屏障 + 受理序号 + 拒绝分类」可能大部分不需要——冲突窗口极短（仅指针 CAS），`try_exclusive` 的「冲突即报错」或轻量重试即够，除非确有「多写者排队」语义需求。

**结论**：两能力「未实现但模型支撑」，技术风险低。登记为**后置横向能力批次 P-IO-8**（不含在 P-IO-6），解冻不依赖。

### 1.11 磁盘布局与统御（P-IO-7 authority，2026-08-23 定稿）

> 本节给 P-IO-7 定 authority。核心决策：**两磁盘布局（扁平/单文件）平级分展开，内存布局（`LoadedState`）为中介，块物化格式（IPC/parquet）为与布局正交的新轴；统御 = 统一数据界面（`TbLayout` trait 泛型化，规范先行，为 P-IO-8 横向能力前置抽象）。** 层化目录（树中心布局）**独立成工单、写作完送挂起**（三关系裁定见 §1.11.8）。P-IO-7 拆三阶段：统御 → 扁平 → 单文件。

#### 1.11.1 两件套：内存中介、两磁盘布局、双向物化

| 层 | 概念 | 现形态 |
|---|---|---|
| **内存布局（中介真源）** | 树运行时形态 + content-addressed 桶 + 寻址索引，**磁盘无关** | `LoadedState { image: TreeImage, bucket: Bucket, index: XPathIndex }`（tb_library.rs:42）已存在 |
| **两磁盘布局** | ①扁平目录（块中心）②单文件（打包中心）；平级两布局，共享内存中介 + 对象字节生产工具 | ①当前 ParquetDir ②v4 容器已有一半 |
| **双向物化格式（块层新轴）** | `Ipc`（默认，mmap 零拷贝）/ `Parquet`（可选，压缩/投影，读=内存重建） | 当前全 IPC；parquet 依赖已在 |

**三种布局哲学（2026-08-23 定）**：扁平 = **块中心**（content-addressed 平铺、去重，树由全局树字节 + 引用表重建）；单文件 = **打包中心**（连续区 + 对象目录，物理便携）；层化 = **树中心**（目录结构即树的物理真相，每层自描述 schema）——层化**不在此批**，独立工单挂起（§1.11.8）。

**ParquetDir 已过时（正名）**：`parquet_dir.rs` 的名字源自 v4 表空间载体名；TB 对象库复用了该 layout 类型但存的是 **Arrow IPC**（`tb-blocks/{address}.bin` = envelope，`encode_batch`/`decode_batch`）——名字与实际行为（IPC 对象库）早已脱节。**扁平阶段重命名为 `FlatDir`（扁平目录）**，回归「content-addressed 对象库扁平物化」本意。

#### 1.11.2 非 Arrow 边界（严格限块层）

- 非 Arrow 数据 **≤ 数据块 payload 级**；默认全 Arrow（非 Arrow 由下游 opt-in，经物化器显式指定）；
- **单文件布局强制全 IPC（Arrow）**——需 mmap 连续，parquet 无法零拷贝映射；**parquet/非 Arrow 只对扁平起效**；
- `Blob`（任意字节）/ 注册块（opaque `Named`）天然非 Arrow，已是块一等公民（`BlockCaps::Opaque|Arrow`）；
- **元数据层（树字节/引用表/commit）恒 canonical Arrow IPC**——内容寻址 + 双哈希铁律 + verify L1–L3 基石，**不可物化化**；
- 本阶段只留「可嵌入其他保存方式的 hook（物化器接口）」，**实现全部为 Arrow 物化**（IPC 默认，parquet 亦为 Arrow 系物化）。

#### 1.11.3 双向物化格式（块 payload 物化器）

| | **Ipc 物化**（默认） | **Parquet 物化**（可选，本阶段实现） |
|---|---|---|
| 本质 | 内存 Arrow → canonical IPC（`encode_batch`），内存什么样磁盘什么样 | Arrow → parquet 列存（`ArrowWriter`），读 = 内存重建（硬盘副本）|
| 零拷贝 mmap | ✅（P-SH 共享吃 buffer 的红利）| ❌ |
| 压缩 / 列投影 | ❌ | ✅ |
| 适用块 | Table/Sequence/Kv/Blob（全块类）| 仅 `ArrowTable`（RecordBatch 形态）|
| 适配布局 | 两布局 | 仅扁平 |
| 依赖 | 已有 | `parquet` crate 已在 Cargo.toml（v4 ParquetDir 在用），arrow-rs 读写现成 |
| 身份/地址 | `address = hash(IPC)`（= 现状 golden 17）| `address = hash(parquet)`（物理随压缩变）|

**物化选择粒度（2026-08-23 定）**：布局配置默认 + 块类型约束——`ArrowTable` 可 IPC 或 parquet，`Blob`/opaque `Named` 恒原生字节；**不做逐块 API 参数**（parquet 仅 `ArrowTable`）。

**「纯 IPC = 单文件的原理，仅连续化」**：IPC 物化即内存 buffer 连续字节，单文件布局 = 多对象连续 buffer 拼成大连续区 → 天然 mmap。这正是「单文件强制 IPC」与「双向物化」的统一点。

#### 1.11.4 身份 ⊥ 地址（物化无关，正式落地 §1.3 铁律）

- **`block_ref_id`（语义身份）恒物化无关** = `canonical_digest(kind.domain(), [canonical_payload])`——同逻辑块无论 IPC 还是 parquet 物化，身份恒同（content-addressed 去重被物化格式边界隔离，不同物化 = 不同物理对象、同语义身份）；
- **`block_blob_address`（物理地址）随物化** = `canonical_digest(b"tb-blob", [物化字节])`；
- **写入双编码一次完成**：先有内存 Arrow → 编 canonical payload 取身份 → 编（IPC 或 parquet）取物理字节；
- **读取/verify 格式感知**：读 address 指向对象 → 探测文件头魔术（Arrow IPC `ARROW1` / parquet `PAR1`）→ 对应物化器 decode 到块 → 重算 canonical payload 比对 `RefId`；
- 引用表 `address` 列指向物理对象，行制不变；bucket 重开按探测分派 decode 装桶。

#### 1.11.5 统御（统一数据界面，规范先行）

统御 = 两磁盘布局的**统一数据界面**，承载不随布局漂移的公共面：

- **hold 形态（2026-08-23 定）**：`TbLayout` **trait 泛型化**——`TbLibrary` 泛型/盒子化持有布局，长期可扩展、避免逻辑散在各 `match`；
- **转换面**：写（`LoadedState` 物化 → 布局定位写）、读（布局物理读 → 物化器 decode → `LoadedState`）；
- **物化器 trait**：`BlockMaterializer { encode(block) → physical, address(physical) → Digest, decode(physical) → block }`，`Ipc` 与 `Parquet` 两个实现，注册可扩展（非 Arrow 未来 hook）；
- **锁 / 并发原语**：跨布局统一的 `metadata_lock` 语义（`FileLock::try_exclusive` 冲突策略，P-IO-8 细化）；
- **只读 / 同步 / 崩溃恢复**：统一界面暴露，**P-IO-8 消费**——统御先把界面立住，P-IO-8 的 sync/并发写/只读基于它统一实现，不漂移成两份；
- **规范先行**：统御是规范 + 物化器 + 两布局实现挂靠的基座；下游布局必须基于统御规范实现。

#### 1.11.6 P-IO-7 三阶段

| 阶段 | 内容 | 依赖 |
|---|---|---|

## 2. xpath 寻址归一（P-XU 批次规范，2026-08-22 定稿）

> **取代声明（归档修订，依 `_dev/README.md` §3 政策）**：本节**取代**归档工单《树与桶模型改造》01 §4.4（xpath 寻址）中 `Step::Key` 的相关语义，及 §4.4.2 的 N-8 决策（Key 步规范字节 0x4b）——Key 步删除后，N-8 所针对的「`Index(3)` 与 `Key("3")` 显示同为 `[3]`」碰撞不复存在（归一后 `[...]` 仅 Index 一种含义）。

### 2.1 背景与动机

- **触发**：P-IO-4 验收裁定 1（04 验收批注）——String-keyed Map 块叶子的引用表 xpath（typed `leaf_refs` → `Key` 步 0x4b）与 verify 意象重算（Named 定位 → `Field` 步 0x46）不一致 → verify 对合法 typed 树误报；
- **复核发现 `Step::Key` 是半接通概念**：`DynamicNode` 导航不消费（存储为 `BTreeMap<String, _>`，纯 Field 寻址）；canonical 树表不区分（Named 定位吞 String 键，A-2 §5.3 规则 3 类型擦除）；typed bytes16 map + `TreeNode` derive 编译不过（`.key()` 不接受 `[u8;16]`，现存测试未覆盖该组合）；image walk 仅在 key16 上产出且 `from_utf8_lossy` **非单射**（xpath 空间碰撞隐患）；
- **考古（工单所有者陈述，2026-08-22）**：Key 步源自 Python 侧以 map 伪造分片操作的遗留设计；Rust 侧有真正的 Sequence 多重性与 chunk 组，无此包袱。

### 2.2 规范（每个唯一地址有且只有一种写法）

1. **Step 枚举两变体**：`Field(String)`（注入编码 0x46 + u64 长度前缀）与 `Index(usize)`（0x49 + 定宽 8 字节小端）。`Step::Key` 与 0x4b 编码**删除**；`XPath::key()` 构建器删除（调用方改 `.field()`）。
2. **命名子统一 Field**：struct 字段与 String map 键原样作 Field 名；**bytes16 map 键 = Field(小写 hex，32 字符)**（单射编码；与 `layout/tb.rs` `format_hex` 约定一致）。同形状内无碰撞（String 键与 hex 键不会出现在同一位置）；跨形状同路径无共享索引面。
3. **解析语法**：`[...]` 仅 Index（内容必须解析为 usize，否则报错）；map 条目的唯一拼写 = `/map_field/key`；Display 同语法。旧 `[key]` 语法删除（出现即 parse error）。
4. **Locator 层不动**：canonical 树表的 Named/Keyed/Positioned 定位是 A-2 冻结格式（TreeId golden 11–15 不变）；本归一只动**寻址层**——Keyed 定位派生 `Field(hex)` 步、Named 定位派生 `Field` 步、Positioned 派生 `Index` 步。
5. **单射性（正确性论证）**：单节点的子条目寻址同质（全命名或全位置，模板锁定）⇒ 同一树内「Key→Field 折叠」无碰撞；「struct 字段 vs map 键」的差异归模板层（「一切解释在树」铁律的贯彻）。归一后 typed `leaf_refs` 与意象重算**按构造同形**——verify 行集比对恢复精确。
6. **可达性边界（诚实记录）**：寻址**规范字节层**（长度前缀编码）任意 UTF-8 键安全往返（引用表 xpath 列为 Binary，不经 `/` 解析）；**解析/显示层**对含 `/`、空串的 map 键不保证 display→parse 往返（沿用 v4 Name 同类约束的精神）——此类键经强类型主路与规范字节层可达，人面 xpath 语法不可拼。
7. **编解码**：`canonical_xpath_bytes` / `xpath_from_canonical_bytes` / `xpath_hash` 的 0x4b 分支删除；解码遇 0x4b 报错（负向测试）。

### 2.3 影响面与 golden 义务

- **消费面**（编译器驱动迁移，删变体漏改处编译报错）：`xpath/mod.rs`（枚举/解析/Display/构建器）、`index/mod.rs`（0x4b 解码删除）、`layout/tb.rs`（walk 的 Keyed → `Field(hex)`，替代 lossy 编码）、`tree-space-derive` map 臂（`.key` → `.field`；bytes16 用 hex——**顺带修复 bytes16 map 的编译 gap**）、测试（n5 行为更新）。
- **golden 零字节重冻结**（已核实）：n5 为行为断言非字节常量；TreeId（Locator 层不动）/ TB 引用表 / 块 golden 均无 Key 步 xpath 字节；`xpath_hash` 无 Key 冻结。既有 golden 断言不变即为本批次的回归守护。
- **新增测试义务**：① String-map 块叶子端到端（`BTreeMap<String, Table>`：commit → **verify clean** → 重开 Field 拼写查询命中 → typed project 往返）；② bytes16 map 端到端（双 derive 编译 + Field(hex) 拼写全程）；③ `[key]` 解析报错；④ 0x4b 解码报错。
- **P-IO-5 必办项 1 由本批次取代消化**：原「String-keyed Map 块叶子引用表 xpath 约定统一 + verify 覆盖类扩展」（P-IO-4 验收裁定 1）关闭——归一后两侧按构造同形，verify 恢复精确。

## 6. 纪律

1. **先文档后实现**：任何偏离本文件的实现决策，先更新本文件 + `03-开发状态.md` 记录，再动代码。
2. **v4 追加式演进（本工单关键纪律，区别于前一工单的「v4 零改动」）**：本工单**必然触及** v4 路径（commit 扩展、blob 存储新对象）。约束为——旧数据必须可读（旧读端遇新字段合理降级）；既有 v4 golden 字节不变（新增字段进新 golden 清单）；`DESIGN_VERSION` 维持 `"v4"`（§1.8 议题 4 的裁定生效前不得擅动）。
3. **模型规范冻结**：块/树编码格式（归档工单 §2/§5）本工单一律不改——发现缺陷先回归档工单流程裁定（归档修订政策：活跃工单显式声明取代）。**§2（P-XU）即为该机制的一次行使**：对归档工单 01 §4.4（xpath 寻址的 Key 步语义）的显式取代——仅寻址层，块/树编码格式（envelope、canonical 树字节、TreeId/RefId 公式）仍冻结。
4. **领域无关**：两 crate 源码禁止业务语义字面量（polars 桥 crate 的依赖与命名不受此限，但仍禁止业务语义）。
5. **依赖纪律**：tree-space / tree-space-derive 零新增第三方依赖；`tree-space-polars` 允许依赖 polars（P-PB 立项时定版本策略）。
6. **golden 覆盖**：降级对象、块/树 blob 地址、引用表、commit 追加列、重开等价性、GC 完整性、ephemeral 剪枝记录（清单 §1.9.7，随批次里程碑冻结）。
