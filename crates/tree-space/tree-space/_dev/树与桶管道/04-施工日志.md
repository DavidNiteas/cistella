### 总体结论

**三个里程碑全部通过验收，予以关闭。** 审计内容与结论：

- **规范符合性逐条核对通过**：块 blob（envelope 全字节，tb-blocks/）、树字节 blob（tb-trees/）、引用表三列（xpath/ref_id/address，canonical 行序，tb-refs/）、commit 七列追加（三 nullable FSB16，纯 v4 全 null）、GC 单跳（只读引用表、零格式解释）、降级语义（空 v4 tree + 空 metadata 自举快照）——与 01 §1.9 全部一致。
- **四份施工前 §7.3 修订全数接受**（格式级空白补齐，未改变已裁定语义）：
  1. 地址域 `b"tb-blob"` / `b"tb-tree-blob"` / `b"tb-refs"`——与语义域 `tb-block-*`/`tb-tree` 世代隔离，铁律完整；
  2. `tb_commit_id = canonical_digest(b"commit", [seq, parent, root_tree_id, tree_blob, refs])`——已与 v4 原始四 part 公式核对：同域但 part 数不同（长度前缀 ⇒ 字节必异，无碰撞），恒定两列（空 tree/空 metadata）不入域正确；纯 v4 commit 原公式字节与 id 不变（genesis 仍 4 列有测试守护）；
  3. 空 metadata 快照 = `BootstrapImage::built_in()` 经 v4 `metadata_ref` 公式——与创世纪提交同一对象，内容恒定、全库一次写出，旧读端自举为「空表集」；
  4. verify 覆盖类边界——见「裁定 1」。
- **golden 审计通过**：16–19 以 `assert_eq!` 绝对常量冻结（含七列 commit 帧 5028 hex、三列引用表 2612 hex 完整字节）；20–21 为行为断言（重开等价性 + 旧读端降级）。
- **红线合规**：纯 v4 写路径（create/publish/write_commit/write_tree/metadata_ref）字节零改动（diff 审计逐函数确认）；v4 路径改动全部为追加式（路径访问器可见性、read_commit 容错解析、GC 可达集/sweep 扩展）；`DESIGN_VERSION="v4"` 未动；零新增依赖；领域无关；无 git 写操作、无 target/ 副产物。

### 裁定

1. **verify 覆盖类边界（String-keyed Map 块叶子）——接受为已声明限制，但登记为 P-IO-5 必办项。** 验收方核实了边界非空洞：`tree-space-derive` 支持 `(Block, Map)` 字段语法，`BTreeMap<String, 块类型>` 是合法 typed 树。对该类树：typed `leaf_refs` 产出 `Step::Key`（0x4b），而 canonical 平面条目表不编码「struct 字段 vs String map 键」区分（归档 §5.3 规则 3 类型擦除），verify 的意象重算（`image_leaf_refs`）对 Named 定位统一走 `field()`（0x46）→ 行集比对必不一致 → **verify 对该类合法树误报损坏**（假阴性，非数据损坏；reopen/project 不受影响）。`[u8;16]`-keyed map 不受影响（`key16` 独立定位，意象与 typed 均走 `Key` 步，一致）。**裁定：本里程碑接受（数据完整性无虞、已诚实声明、golden 样本避该类），但闭口必需——登记 P-IO-5 必办：统一 String-keyed Map 块叶子的引用表 xpath 约定并扩展 verify 覆盖类**（该修复触及归档 §5.3 规则 3 的 xpath 语义，属规范层决策，归 P-IO-5，届时回写 01 §1.9.4）。
2. **`xpath_from_canonical_bytes` 的 Index 步解码修正**（0x49 后直接读 8 字节 u64，P-IO-4 日志）：正确——Index 注入编码本就是步内容带长度前缀，0x49 后即 8 字节小端值，无额外长度前缀；初版误读已修，纯新增函数非既有格式变更。接受。
3. **截断树 blob 报 `DigestMismatch` 而非 `PayloadMalformed`**（重开先核对 `tree_id(字节)==root_tree_id`）：合理错误分类（身份不匹配优先于载荷解析），测试断言与实现一致。接受。
4. **伪造文件名负向改为「内容改写、地址名不变」**：正确——地址名语义 = 文件名即地址，非法名按不可解析跳过（合法降级）；内容-地址不一致触发 `DigestMismatch` 是真正的伪造检测路径。接受。

## P-IO-6 authority 讨论定稿（验收方与工单所有者共签，2026-08-22）

> P-IO-6 是**评审型里程碑**。本节记录 authority 落笔前的决策链；规范见 01 §1.10。

- **战略定调（工单所有者）**：V4（表空间模型）最终**完全下线**；树+桶为向所有下游暴露的**唯一最终面**，下游全部为树+桶适配——「我们怎么设计树+桶的服务面，下游就怎么改」。
- **view 定位确认**：view 机制即弥合「桶数据块过于底层」的手段——桶不必被当底层（可存整表，polars 式），view 从块/表投影组织业务视图。两条数据路径（原生表 / 投影表）均完备，不存在「服务层」缺口：**否决**在 `TbLibrary` 之上再竖纵向服务层的设计（我早前提过，被所有者纠正）。
- **sync/并发写可行性论证（技术判断，非实现）**：
  - 当前树+桶 `TbLibrary` 无 sync；并发写仅 `metadata_lock` → `FileLock::try_exclusive`（跨进程**非阻塞**独占锁，冲突即 `LockUnavailable`），无 v4 M12 的 barrier/受理/wait；
  - **content-addressed 不可变追加模型**让两项能力退化为单调幂等操作——sync = 对象传输（git fetch 式，幂等/增量/去重）、并发写 = 唯一竞争点收敛到 committed 头指针一处 CAS；v4 表空间的整表空间锁 + reader/writer 可见性在此模型下大部分不需要；
  - 结论：**「未实现但模型支撑」**，技术风险低。据此把 §1.8 #5 从「P-IO-6 评审时定范围」改判为「解冻后横向能力批次 **P-IO-8**」，明确**不在 P-IO-6 施工**。
- **P-IO-6 三个实质**：① 树+桶即最终面的契约**定稿声明**（§1.10.1–1.10.2，现有能力契约化）；② **全要素 acceptance**（§1.10.3：跨 crate 消费侧闭环 + 主数据路径 + view 组织 + v4 降级）；③ **解冻裁定**（§1.10.4：`联合开发.md` §3.2 冻结解除回写）。
- **V4 下线过渡窗登记**（§1.10.6）：过渡期维持 §1.8 #3（`DESIGN_VERSION` 维持 v4）+ §6 纪律 2（旧数据可读），保证旧库可开可迁；下线路径待下游迁移完成后再评估，不在本里程碑执行。
