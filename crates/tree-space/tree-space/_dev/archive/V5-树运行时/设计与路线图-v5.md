## 0. 背景与动机

v4 的 `tree-space` 把「数据后端」建模成一张**只有 table 叶子**的扁平表空间：所有的磁盘对象都是 Arrow IPC / parquet，叶子只能是一个 `RecordBatch`。这一模型已支撑了 tree-space M0–M12、mzml-db、uni-mass-db 的落地。

但它有两个结构性限制，正是本轮改造要解决的：

1. **叶子只能是表**：真实业务里，一个「库」既有表（最重要的东西），也有结构体、标量、矢量、任意字节块、以及「指向别的叶子的引用」。把后几类硬塞成单列表是语义 hack。
2. **结构无统一模型**：v4 里「结构」由 `domain-metadata`/`table-metadata` 等**运行时元数据表**表达，而「数据」由 content-addressed blob 承载——两者是割裂的。缺少一个统一的、编译期可校验的「树」来规定整个索引空间。

根本方向（已与 NestedTreeModule 对齐）：把 `tree-space` 改造成 **NestedTreeModule 的 Rust 运行时版本**——一颗**编译期确定形状、运行时只允许数量与空态变化**的树；树承载「寻址结构 + 结构 schema」，叶子数据类型是开放的（table 只是默认的主实现）；叶子数据本体仍走 content-addressed 扁平 store。

## 1. 新设计目标（核心不变量）

> 沿用 v4 §1.2 规范性词汇（MUST/SHOULD/MAY、读路径/写路径、发布）。

1. **树是唯一索引空间（MUST）**：一颗嵌套树规定整个库的寻址空间与结构 schema；「哪个 xpath 合法、该位置叶子是什么类型」只能由树（编译期模板）决定。
2. **编译期确定形状（MUST）**：树的形状（有哪些字段、每个字段的类型与基数修饰）在编译期锁死；运行时**只允许空态（Option 有无）和数量（容器长度/键集合）变化，不允许类型变化**。实例是什么就是什么。
3. **树不存数据 payload（MUST）**：树的运行时实例只承载「拓扑 + 结构 schema + 叶子引用句柄（`RefId`）」；叶子数据本体存在 content-addressed store 中，由 `RefId` 引用。
4. **叶子类型开放（MUST）**：叶子不止 table（table 是默认主实现），还覆盖结构体、标量、矢量、字节块、引用；一切叶子都必须实现 `Leaf` trait，其 schema 是 table-schema 的推广。
5. **xpath 是唯一寻址（MUST）**：节点/叶子的访问统一走 xpath（类型步 `/field` + 实例步 `[i]`/`[key]`）。
6. **内容寻址仍是存储根基（MUST）**：物理 blob 仍按 `content_hash` 内容寻址、不可变、可去重、可达性 GC；`committed` 仍是唯一可见性点。这条与 v4 完全一致，不因叶子类型扩展而改变。
7. **双哈希铁律（MUST）**：xpath 哈希（索引键，可碰撞）与 `content_hash`（存储地址，全内容）严格分离，不得混用（见 §9）。

## 2. 核心概念与术语

| 术语 | 定义 |
|---|---|
| **模板（Template）** | 编译期类型（`struct`/`enum` 组合）定义树的形状；无运行时实体，编译期即 DAG |
| **树实例（Tree Instance）** | 运行时轻量结构，承载「拓扑（基数）+ 结构 schema + 叶子引用」；不承载 payload |
| **节点（Node）** | 树的内部分支点，持有 child；由 `#[derive(TreeNode)]` 的 struct 实现 |
| **叶子（Leaf）** | 树的终止点，持有值；所有叶子实现 `Leaf` trait |
| **基数（Multiplicity）** | `Single`/`Optional`/`Sequence`/`Map` 四态（§6） |
| **容器** | `ZeroOrMore` 字段的运行时形态：`Vec<T>`（顺序）或 `BTreeMap<K,T>`（按键） |
| **数组叶子（Array Leaf）** | 指「叶子内部数据是数组」（如数值向量，单 blob 存）；**区别于容器**，基数不变 |
| **domain 标签** | 贴给节点/叶子的性质标签（trait），与树结构正交（§7） |
| **RefId** | 内容寻址引用句柄 = `LeafHash`；叶子 payload 在 store 中的身份 |
| **xpath** | 唯一寻址路径：类型步 `/field` + 实例步 `[i]`/`[key]` |
| **store** | content-addressed 扁平存储：`RefId → blob` |

> **术语铁律**：容器（`Vec<Node>`，基数可变）与数组叶子（叶子值里是数组，基数不变）是两回事，行文与命名必须区分，禁止混用。

## 3. 三层架构

| 层 | 职责 | 运行时实体 | 承载 |
|---|---|---|---|
| **模板** | 编译期类型，定义合法 xpath + 叶子 schema + 基数缩写 | 无（编译期 DAG） | 结构**形状** |
| **树实例** | 运行时结构 | 有，但轻 | 拓扑（`Vec` 长度 / `Option` 有无 / `Map` 键集）+ 每叶子的 `RefId` |
| **store** | payload | 有 | 叶子数据本体（content-addressed blob） |

```text
模板（编译期）                   树实例（运行时，轻量）             store（运行时，重）
#[derive(TreeNode)]              Experiment {                     blobs: BTreeMap<RefId, Vec<u8>>
struct Experiment {              ── 实例化 ──►   runs: Vec<Run>        ▲
    runs: Vec<Run>,                              meta: Some(RefId)    │ content-addressed
    meta: Option<Metadata>,                      x: LeafSlot::Ref(id)─┘
}
```

一个「库实例」= 一根从模板实例化的树实例 + 一张 store（`RefId → blob`）。

## 4. 树元素：节点 + 叶子

树上有且仅有两类元素。

**节点（Node）**：`trait TreeNode`，由 `#[derive(TreeNode)]` 为每个节点 struct 实现。为保持 dyn 兼容（`Box<dyn TreeNode>` 承载弱类型桥），静态元数据表分离到一个独立 trait `TreeNodeMeta`：

```rust
// 静态元数据（含 const，故独立于 dyn 友好的导航 trait）
pub trait TreeNodeMeta: 'static {
    const META: &'static NodeMeta;              // derive 生成的静态字段表
}

// 导航 trait（dyn 友好：无 const/关联类型/Self:Sized 方法）
pub trait TreeNode: 'static {
    fn get(&self, xpath: &XPath) -> Result<AccessOut>;      // 弱类型桥（strict，不可达报错）
    fn get_best_effort(&self, xpath: &XPath) -> (AccessOut, XPath);  // 尽力导航：返回到达值 + 未消费的剩余 path
    fn set(&mut self, xpath: &XPath, v: LeafSlot<Box<dyn Leaf>>) -> Result<()>;  // N-7 落地
    fn leaf_refs(&self) -> Vec<(XPath, RefId)>;             // 遍历所有叶子引用（供 GC/verify/序列化）
}
// 注：derive 生成的 get 内部做 `Box::new(self.field.clone())` —— clone 在具体类型上完成（用户 struct 需额外 derive Clone），不在 trait 内强加 Clone supertrait。
```

```rust
pub enum AccessOut {                    // 弱类型桥的返回值：叶子 trait object、子节点或外置引用
    Leaf(Box<dyn Leaf>),
    Node(Box<dyn TreeNode>),
    LeafRef(RefId),                     // 叶子外置到 store：树实例只持 RefId（N-7 引入）
}
```

**设计二分（关键）**：
- **强类型主路**：热路径直接字段访问 `exp.runs[3].x`，零成本、编译期类型；
- **弱类型桥**：xpath 字符串、序列化、schema 反射走 `get`/`set`，用 `Box<dyn Leaf>` 兜底，只在这几条非热路径出现，不得腐蚀主路。

## 5. 叶子类型系统（Leaf trait）

### 5.1 核心 trait

```rust
pub type LeafHash = crate::ids::Digest;   // [u8;16]，xxh3-128

#[derive(Copy, Clone, PartialEq, Eq, Hash)]
pub struct RefId(pub LeafHash);

#[derive(Copy, Clone, PartialEq, Eq, Hash)]
pub enum LeafKind { Table, Scalar, Struct, Array, Blob }

// dyn 兼容实现（技术调整，见 §14 决策 #6）
pub trait Leaf: Send + Sync + 'static {
    fn kind(&self) -> LeafKind;                 // 取代 const KIND（dyn 兼容）
    fn content_hash(&self) -> LeafHash;         // 内容寻址核心
    fn write_blob(&self, out: &mut Vec<u8>);    // → 规范字节（也是哈希的输入）
    fn schema(&self) -> SchemaDesc;             // 无关联类型，直接返回描述
}
// read_blob 移到各具体 leaf 的静态方法（try_read_blob / read_blob），
// 因为 `Self: Sized` 方法使 trait 无法作为 dyn Leaf；
// store 侧经 N-3 的 read_leaf 静态 LUT 做类型擦除分派。

pub trait LeafSchema: Send + Sync + 'static {
    fn describe(&self) -> SchemaDesc;
}
```

### 5.2 内置叶子实现（默认主实现是 Table）

| 叶子 | 内容 | Schema | 落盘定位 |
|---|---|---|---|
| `Table` | Arrow `RecordBatch` | `TableSchema`（列名 + Arrow Field） | **主实现**；复用 v4 canonical IPC 编码 |
| `Scalar` | 数值/字符串/布尔/时间等标量 | 标量类型 | 内联或单值 blob |
| `Struct` | 小结构体（字段是标量/其他叶子） | 字段表 | 目录化或单 blob |
| `Array` | 叶子内部是数组（数值向量等） | 元素类型 + 长度 | 单 blob（**基数不变**，区别于容器） |
| `Blob` | 任意字节块 | 无/字节长度 | 单 blob |

> **引用不是叶子类型**：叶子是"什么类型"由编译期模板（字段类型 + 注册表）决定，`RefId` 只负责"数据在哪"。「某一叶子的值外置到 store」由叶子槽 `LeafSlot::Ref(RefId)`（§5.3）统一表达，DAG 共享由内容寻址自动实现（相同内容 = 相同 `RefId`）。故 `LeafKind` 不自列 `Ref` 变体。

`Table` 实现示例：

```rust
pub struct Table { batch: RecordBatch }

impl Leaf for Table {
    const KIND: LeafKind = LeafKind::Table;
    type Schema = TableSchema;
    // content_hash / write_blob / read_blob 复用 v4 的 canonical IPC 编码（含 in_hash=false 列规则）
}
```

### 5.3 叶子槽（LeafSlot）：值 vs 引用

叶子在树实例中的一个字段位置，要么内联、要么外置到 store：

```rust
pub enum LeafSlot<L: Leaf> {
    Inline(L),     // 小值内联在树实例里（Scalar/Struct）
    Ref(RefId),    // 大值外置到 store，树实例只持 RefId（Table/Array/Blob）
}
```

- **内联/外置是策略，不是叶子类型属性**：默认 `Scalar`/`Struct` 内联、`Table`/`Array`/`Blob` 外置，可显式覆盖；具体策略与 blanket impl（`Leaf for Box<dyn Leaf>` 等弱类型桥配套）在 **N-7** 定型。
- 这是「树不存 payload」的落地：外置时树实例只占 16 字节 `RefId`，数据本体在 store。

## 6. 基数与可空（部分动态）

编译期从字段类型自动推断基数（`#[derive(TreeNode)]` 负责）：

| Rust 字段类型 | Multiplicity | xpath 实例步 | 语义 |
|---|---|---|---|
| `T` | `Single` | `/field` | 恰好 1 个 |
| `Option<T>` | `Optional` | `/field` | 可空 0..1 |
| `Vec<T>` | `Sequence` | `/field[i]` | 顺序容器 |
| `BTreeMap<K, T>` | `Map` | `/field[key]` | 按键容器 |

```rust
pub enum Multiplicity { Single, Optional, Sequence, Map }
```

> 命名说明：此处用 `Multiplicity`，与 v4 `types::Cardinality`（domain child 的**运行时**基数声明）区分——v5 字段基数是**编译期从字段类型推断**的。四态对应：`Single`=`T`、`Optional`=`Option<T>`、`Sequence`=`Vec<T>`、`Map`=`BTreeMap<K,T>`。

**「部分动态」的精确定义**：树实例一旦从模板实例化，字段集合与每个字段的类型即固定；运行时唯一可变的是 `Option` 的 Some/None、`Vec` 的长度、`BTreeMap` 的键集合。**类型不可变**由 Rust 类型系统在编译期自然保证，无需运行时校验。

**`BTreeMap` 键约束（MUST）**：`K` 必须是稳定可复算的键（`String` 或 `[u8;16]`）；derive 应静态拒绝「任意整数做 Map 键」等会引入插入序不稳定的写法。

## 7. domain 标签

domain 不再是树上的「层级/分组」，而是**贴在节点/叶子上的性质标签（trait）**，与树结构正交：

- 「叶子必定属于叶子 domain」= 一切叶子必须 `impl Leaf`（内置约束）；
- 细分 domain 用 marker trait，同类 domain 有共同性质，由 trait bound 保证：

```rust
pub trait TableDomain: Leaf {}      // 贴上「表」标签
pub trait SpatialDomain: Leaf {}    // 贴上「带空间语义」标签
```

- 标签贴在**模板（类型）**上（`impl SomeDomain for T`），实例继承；运行时可查面用 `LeafKind`（§5.1）。

这一正交化呼应 v4 §4 的「path 与 type identity 分离」，并将其确立为「结构（xpath）⊥ 性质（domain 标签）」的通用原则。

## 8. xpath 寻址与字段注册表

### 8.1 XPath 与 Step

```rust
pub struct XPath { steps: Vec<Step> }

pub enum Step {
    Field(String),   // /field
    Index(usize),    // [i]
    Key(String),     // [key]
}
```

xpath 有**两层**，必须显式区分：

- **类型路径**（schema 级）：纯 `/field` 步，稳定、可 digest；
- **实例路径**（数据级）：含 `[i]`/`[key]` 步，指向具体实例。

### 8.2 字段注册表（`#[derive(TreeNode)]` 编译期生成）

Rust 无运行时反射，xpath 按名寻址必须靠 derive 在编译期生成「字段名 → 访问器 + 类型 + 基数 + schema」的静态表：

```rust
pub struct FieldMeta {
    pub name: &'static str,
    pub multiplicity: Multiplicity,
    pub target: FieldTarget,
}

pub enum FieldTarget {
    Node(&'static NodeMeta),
    Leaf { kind: LeafKind, schema: &'static LeafSchemaMeta },
}

pub struct NodeMeta {
    pub type_name: &'static str,
    pub fields: &'static [FieldMeta],
}
```

derive 展开示例（`#[derive(TreeNode)] struct Experiment { runs: Vec<Run>, meta: Option<Metadata> }`）：

```rust
impl TreeNode for Experiment {
    const META: &'static NodeMeta = &NodeMeta {
        type_name: "Experiment",
        fields: &[
            FieldMeta { name: "runs", multiplicity: Sequence, target: Node(RUN_META) },
            FieldMeta { name: "meta", multiplicity: Optional,
                        target: Leaf { kind: Metadata::KIND, schema: METADATA_SCHEMA } },
        ],
    };
    // fn get / set / leaf_refs 由同一 derive 生成
}
```

## 9. 索引哈希表与双哈希铁律

叶子数据引用存入一张**扁平的 xpath 索引哈希表**：

```text
xpath_hash → RefId（叶子在 store 中的内容寻址身份）
```

- **索引键用 `xpath_hash`**（`canonical_digest(b"xpath", [...])` 对规范 xpath 字节取哈希），定位叶子引用；
- **碰撞降级（保险丝机制，非主路径）**：`xpath_hash` 命中后，用**完整规范 xpath 字节**二次确认；不一致即沿碰撞链继续。128-bit 碰撞概率天文数字，降级仅为严谨性兜底；
- **双哈希铁律（MUST，沿用 v4 §8）**：
  - `xpath_hash` = 索引键，**可以**碰撞，绝不用于物理寻址；
  - `content_hash` = 全内容哈希，用于 blob 地址/去重，**绝不**被 xpath_hash 或语义表 digest 替代；
  - 违反即重蹈 v4 已排除的「仅差在非哈希列的表同地址碰撞丢数据」问题。

## 10. IO 布局（按叶子类型分派 + 注册）

### 10.1 布局形态

**落地方式（与初稿的偏移）**：v4 的三布局（`src/layout/`）是**表专用**的磁盘协议（`StorageLayout` + `TableBytes` + commit-tree），本改造**不改动**它们。任意叶子的内容寻址存储与布局分派以**新增平行层**交付：

| 组件 | 位置 | 角色 |
|---|---|---|
| `LeafStore` | `src/store/`（N-9） | `RefId → StoreBlob{kind, bytes}` 自描述扁平 store（去重/verify/GC） |
| `LeafIoDriver` 三驱动 | `src/io/layout.rs`（N-10） | Memory / SingleFile / Directory 对任意叶子的 roundtrip/verify/GC/reopen |

| 驱动 | 角色 | 叶子落盘方式 |
|---|---|---|
| `MemoryIo` | 正确性 reference | 叶子内存直存（`RefId → LeafFrame`） |
| `SingleFileIo` | 单文件追加容器 | `LeafFrame`（`[kind_len][kind][payload_len][payload]`）追加 + reopen 重放 |
| `DirIo` | 目录化 content-addressed | `blobs/<ref-id>.leaf`（自描述帧） |

- v4 的 `Memory/SingleFile/ParquetDir` 三布局及其 `StorageKind` 命名**原样保留**，仍是表数据的磁盘协议 authority；v5 的任意叶子走上述平行 store/驱动，二者井水不犯河水。
- 表仍是叶子一种：`Table::write_blob` 复用 v4 canonical IPC 编码，因此 `Table` 叶子经平行 store 读写无损（`table_backward_compat`）。

### 10.2 注册机制（编译期，漏实现即编译报错）

两条路径（与 §5.1 呼应）：

1. **静态路径**（编译期已知类型）：`impl Leaf for T` 即「注册」；漏任何必需方法（如 `write_blob`）编译期报 `trait bound T: Leaf is not satisfied`，**不落到运行期**。
2. **动态路径**（store 按 `LeafKind` 反序列化 blob）：用**静态 LUT（`match kind`）+ 枚举穷尽检查**收集「kind → reader」：

```rust
pub struct LeafReader {
    pub kind: LeafKind,
    pub read: fn(&[u8]) -> Box<dyn Leaf>,   // 类型擦除反序列化入口
}

// 集中式静态分派表（位于 tree-space 核心内，覆盖所有内置 LeafKind）
pub fn read_leaf(kind: LeafKind, bytes: &[u8]) -> Box<dyn Leaf> {
    match kind {                       // LeafKind 是枚举：漏分支 = non-exhaustive 编译报错
        LeafKind::Table  => Box::new(Table::read_blob(bytes)),
        LeafKind::Scalar => Box::new(Scalar::read_blob(bytes)),
        LeafKind::Struct => Box::new(Struct::read_blob(bytes)),
        LeafKind::Array  => Box::new(Array::read_blob(bytes)),
        LeafKind::Blob   => Box::new(Blob::read_blob(bytes)),
    }
}
```

- **静态 LUT 是首选，零第三方依赖**：Rust 的 `match` **穷尽性检查本身就是"编译期注册 + 漏注册即报错"**——`LeafKind` 新增变体而未在 `read_leaf` 补分支，编译器直接报 `non-exhaustive`，无需任何外部机制；
- 当前 5 个叶子类型**封闭在 `tree-space` 核心内**（非外部插件），无需 `inventory` 的分布式注册价值。
- **新增叶子类型 = `impl Leaf` + 在 `read_leaf` 补一个分支**；两个步骤缺一即编译失败，此为支持新东西的唯一路径。
- 未来若需"外部 crate 定义新叶子类型、核心毫不知情"的插件式开放，再迁 `inventory`（`LeafReader` 形状一致，改动局部）；本节接口不为其预留复杂度。

## 11. 与 v4 的超集关系

本轮是**演进而非推翻**。逐项对照：

| v4 概念 | v5 概念 | 关系 |
|---|---|---|
| 叶子只能是 `table` | `Leaf` 的 `Table` 变体（默认主实现） | 降为特例 |
| Arrow schema | `LeafSchema`（广义） | 推广，table-schema 是其一 |
| `path` + `PathHash` | `xpath` + `xpath_hash` | path 是单层特例 |
| `domain-metadata`/`table-metadata` 运行时表 | 编译期模板 + 树实例 + 字段注册表 | 推广 |
| content-addressed blob（只表） | content-addressed blob（任意叶子，`LeafStore` + `io::layout` 驱动） | 新增平行层；v4 blob 路径保留 |
| Memory/SingleFile/ParquetDir | 按叶子类型分派的 `MemoryIo`/`SingleFileIo`/`DirIo` | v4 布局保留 + 平行驱动 |

**原样保留（MUST 不变）**：content-addressed commit-tree、`committed` 唯一可见性点、`PreparedCommit` 事务模型、verify 读存储真值、可达性 GC、`canonical_digest`、双哈希铁律、sync/transform/service、领域无关守则、MSRV 1.89 + std 原生锁。

命名 `N-*`（nested）。每个里程碑以「消费侧集成测试 + golden/roundtrip」关闭，遵守「先改本文与开发状态、后改实现」纪律。

| 里程碑 | 目标 | 交付物 | 关闭标准 |
|---|---|---|---|
| **N-1 Leaf 地基** | `Leaf`/`LeafSchema`/`RefId`/`LeafKind` + `Table` 第一个实现 | `src/leaf/`（mod/table/scalar） | `Table` content_hash 稳定；write/read roundtrip；leaf golden |

## 14. 已定决策记录（相对设计初稿的偏移）

以下四项已经拍板，正文 §5/§10 已按此回写；任何实现偏离必须先更新本文并回写 [`开发状态.md`](开发状态.md)。

1. **crate 改名**：**不改名**，`table-space` 保留（table 仍是主叶子，名字强调延续性）。候选名 `nested-space` 储备，待对外发布、外部用户被「table」误导时再一击改完；本版本不因改名阻塞实现。
2. **引用的唯一形式**：**已定合并**——去掉独立的 `LeafKind::Ref`，`LeafSlot::Ref(RefId)` 是唯一引用形式（§5.2/§5.3）。DAG 共享由内容寻址自动实现（相同内容 = 相同 `RefId`），叶子"是什么类型"由编译期模板决定，`RefId` 不携带类型。
3. **弱类型桥不引入 `Any`**：**已定不引入**。弱桥只做「类型擦除的叶子操作」（`content_hash`/`write_blob`/`schema`），需要具体类型走强类型主路（编译期已知类型的字段访问 / 静态 `read_blob`）。半途出现「运行期才知道类型又要拿具体数据」的硬场景再补 `as_any` 兜底。
4. **叶子注册用静态 LUT**：**已定用静态 LUT**（`match kind` + 枚举穷尽检查），零第三方依赖（§10.2）。`inventory` 留作未来「外部 crate 插件式定义叶子类型」时的可选迁移，接口不变。
5. **字段基数命名 `Multiplicity`**：**已定**——v5 字段基数修饰四态 `Single`/`Optional`/`Sequence`/`Map`（§6），与 v4 `types::Cardinality`（domain child 运行时基数声明）区分，二者语义不同、井水不犯河水。
6. **dyn 兼容技术调整**：**已定（N-1/N-4 落地）**——`Leaf` 与 `TreeNode` 均需承载在 `Box<dyn …>` 弱类型桥中，而 Rust 的**关联常量/关联类型/`Self: Sized` 方法三者都会破坏 dyn 兼容**。因此实现采用：`Leaf::kind()`（取代 `const KIND`）、无关联类型、`schema() -> SchemaDesc` 直接返回；`read_blob` 移到各具体 leaf 的静态方法且经 N-3 `read_leaf` 静态 LUT 分派；`TreeNodeMeta` 独立承载 `const META`，`TreeNode` 保持纯 `&self` 方法（含 N-7 的 `set`）。§4/§5.1 已按此回写。
