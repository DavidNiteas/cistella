### 3. 默认构造等价性论证（01 §3.3 展开）

- `PluginRegistry::global()` = `LazyLock<PluginRegistry>` 进程静态，初始化后只暴露 `&` 面（不可增删）；
- `PluginRegistry::new()` 自动注册同一组内建（`ArrowIpcBlockPlugin` + `ArrowParquetBlockPlugin` + `Arrow55TreePlugin` + `Arrow55→Arrow55` 恒等 `MemoryConverter`）——与 `global()` **内容逐项等价**；
- 因此本工单全部默认构造路径（flat-dir `create`/`create_with_materialization`/`open`、single-file 三构造器）统一落 `Arc::new(PluginRegistry::new())` 字段；三处路由改走字段后，**同输入下路由结果函数值逐字节一致**（路由只依赖 registry 内容，不依赖静态形态）；
- 验证载具：B1-T1（`t_s_b1_1_default_equivalent`）——默认构造 vs 显式 `new()` 注入：同夹具 → 相同 commit receipt（sequence/commit_id/root_tree_id/tree_blob/refs 全等）→ 相同 verify 计数 → 重开 bucket 内容与行数一致；`plugin_registry()` 行为面与 `PluginRegistry::new()` 一致。
- 残余差异登记（01 §3.3）：写侧 `select_materializer` 内部仍引用 `global()`（红线段，未动）——本工单三处读/验侧路由改造完成后，库实例路由面自洽（测试面 B1-T1/T2 覆盖读侧与验侧）。

### 5. 问题与实现过程说明

1. **TreeNode derive 叶型白名单发现**（实现层面的探查结论，非规范问题）：`tree-space-derive` 的 `target_tokens` 以**字段类型名字符串**白名单判定叶型（`ArrowTable`/`Sequence`/`Kv`/`Blob`/`Value`），任意其他类型（含测试局部自定义 `RegisteredBlock`）被归为**嵌套树节点**（要求 `TreeNodeMeta`/`TreeNode` impl）→ 自定义 Named 块无法直接作 derive 树字段（`leaf_counter` 的 wrapper 恰因字段名撞白名单 `Blob` 而通过）。**解决**：场景 C 的 Named 块走**动态镜像路径**（`TreeImage::new` + `named_field` + `ImageContent::Ref(ref_id)` + `TbLibrary::commit(tree_bytes, leaf_refs, bucket)`——`commit` 输入面本就是「树字节 + 叶引用」，typed/dynamic 共用一条路径，01 §0.1 已述），并保留 `RegisteredBlock` 作为 bucket 块 + `register_block` 进程级注册以演示两套注册面正交。此为实现途径的 C 层选择，不触及 01/02 契约面（未新增依赖、未改库），故不构成规范偏离。
2. **场景 B 的 project 断言 kind 修正**：首版断言退化叶 context `kind == "blob"`，运行观测为 `"table"`（canonical 投影序首个退化叶报错，两叶均退化）——改为 `kind ∈ {blob, table}` + `disk == "arrow-ipc"` 的语义级断言，不绑定字段枚举顺序（组合态按既有语义表达的本意）。
3. **消费侧零引用事实**（前置 `rg` 核查）：mzml-db / uni-mass-db 的 src 与 tests 对 B1 注入面三方法**零引用**，对 `PluginRegistry` 类型名同样零提及——零迁移断言的事实依据，与 01 §4.1「既有构造器行为 = 改造前」一致。
4. 无阻塞问题。PS `Set-Content` 工具链替换一处源码字符串时曾出现编码写入风险，已即时校验（`UTF8Encoding(throwOnInvalidBytes)` 严格解码通过、`cargo fmt` + 全量编译验证）——终态文件为合法 UTF-8，无痕。
