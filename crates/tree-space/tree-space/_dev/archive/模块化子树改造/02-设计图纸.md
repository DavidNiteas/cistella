01 §2 把现状概括为「现有载体：TbLayout trait——每 crate 一个单体 layout」。按代码实际分层澄清如下（后续各节以此为锚）：

|---|---|---|
| **物理存储面** | `StorageLayout`（layout/mod.rs:110-123）+ `TbLayout`（layout/mod.rs:154-312）：TB 三对象通道、commit/boot/versions、块物化 | **零改动**（01 §4 边界） |

三个关键现状事实：

1. **运行时类型面已有"组合"雏形**：`DomainType.includes_type_ids` / `TableType.includes_type_ids`（types.rs:113, 167）+ `expand_domain`/`expand_table` 的同名子合并与冲突拒绝（registry.rs:544-584, 586-619：同 `(kind, type_id)` 子静默合并 571-580、不兼容子报 `TypeConflict` 574-580、重复列报错 610-617）。但这是**运行时值层**的展开规则——不是编译期机制，无"两模式"（正交/合并）之分，无模板身份。模板层的组合语义与它**同构但不同层**（§5.2 对齐表）。
2. **编译期冲突检查现状 = 无**（01 §2 原文）。同路径冲突在今天只会是运行时行为（registry.rs:574-580 / family-meta checker）。

## §1 模板 Rust 载体（拍板点①）

### 1.1 七条语义 → 载体硬约束

| # | 语义（01 锚） | 对载体的要求 |
|---|---|---|
| 1 | 组合发生在编译期（01:8-10） | 模板与组合产物必须是**编译期可检、可常量折叠**的 Rust 项（类型/const），组合声明不得退化为运行时函数调用 |
| 2 | 融合的永远是模板非实例（01:11） | 载体值域 = 结构声明（形状/列契约），**不含任何数据/实例句柄**；载体上不存在"拿两个 `TbLibrary` 做输入"的 API 形态 |
| 3 | 运行期结构不可变（01:12） | 载体不得暴露运行时改形的 API（组合算子只在声明期展开）；运行时面只有投影（读） |
| 4 | 树嵌套远期（01:13） | 载体不预设"叶子=另一棵树实例"的运行时机制，但形状表达不排除叶位扩展（结构上留 Path 抽象即可，无需现在设计） |
| 5 | 两模式：正交编译期报错 / 合并后到覆盖（01:14-16；05:54） | 载体必须让"形状可比较"在编译期可达（正交判定）且"覆盖"可确定性折叠（合并判定）——见 §2.3 拍板点② |
| 6 | 读侧宽容（01:17） | 载体无新增要求（现行 `open_multi` foreign-skip 已是该投影，06 调研 §2-3）——但载体的投影产物不得引入"全量结构强校验"破坏宽容 |
| 7 | 多位置派生：模板与挂载位置解耦（01:40-42；05:97, 107-109） | 模板定义**纯结构**；挂载位置/语义角色在**组合声明**时赋予；坐标系可扩展（study/run 现行 + lib 远期）→ 载体需要"模板"与"挂载"两种正交的声明单位（§3） |

另加两条下游硬需求（05 锚）：

- **层级标注叶子**：R2 #4 geo 树跨层级（run 级 geo domain + study 级 consensus 表，05:86）→ 载体要能表达"模板内部条目带槽位锚"。
- **附加树平权**：R3' 附加树与业务树机制完全同构、无 import/无依赖 DAG、端点兼容性归**组合期**检查（05:55, 128-129）→ 载体不得把端点依赖做进模板定义期的类型系统。

### 1.2 候选 a：trait 泛型组合

形态：子模板 = marker 类型 + `TreeTemplate` trait（关联类型/关联 const 承载形状）；组合 = 泛型参数聚合（`type Big = Compose<Host, (PointCloud, Geo, Chem)>`）。

- **表达力**
  - 多位置派生：`Mounted<T, Slot>` 泛型可表达，类型级区分清晰。
  - 层级标注叶子：关联 const 可表达。
  - **正交检查编译期可达性：弱（致命项）**。稳定 Rust 无 specialization / negative reasoning，trait 系统无法对"两个类型的形状是否相交"做编译期判定——要在编译期报错就必须退到宏 + const 断言（那已经是候选 c 的机制），或退到运行期检查（直接违反语义 5）。类型级唯一手段是给每对模板手写互斥 impl，O(N²) 且下游每新增一个模板都要加——不可扩展。
  - 附加树端点：若用类型级端点依赖表达，会把"被引用树"做进模板定义期——违反 R3' 无依赖 DAG 裁决（05:55）。
- **与现有 TbLayout 关系**：无直接耦合（同 b/c——模板层在业务结构面，物理面不感知）。但泛型形状抽取到运行时 `DomainType` 需要 trait 方法或镜面映射，间接层最多。
- **实现成本**：中偏高。宏事实上不可避免（组合声明 + 断言接线），再叠加类型级机器（泛型列表/关联类型投影）；诊断体验差（E0271 类错误深埋 trait 求解）。
- **下游适配**：uni-mass-db 七棵树模板 = 七个类型 + 七套 impl，样板量最大；workspace 组合要引用 uni-mass-db 的类型——可行但最重。

### 1.3 候选 b：const definition 组合

形态：模板 = `const` 数据（`TreeSpec` 结构体，`&'static` 切片承载形状）；组合 = const fn 构建器（`compose_ortho(&a, &b)` / `compose_merge(&a, &b)`）+ `const _: () = assert!(…)` 编译期断言。

- **表达力**
  - 多位置派生：`const fn bind(spec, slot)` 可表达；但"同一模板"在 const 世界里只是值——无类型身份，下游引用与 IDE 导航全靠 const 名约定。
  - 层级标注叶子：spec 数据字段，直接表达。
  - 正交检查编译期可达性：**优（这是 b 的强项）**——const fn 谓词 + const assert 全稳定可用。
  - **容量摩擦（致命项）**：const fn 无堆分配，spec 内变长形状必须用 const 泛型容量（`TreeSpec<const N_ENTRIES: usize>` 之类）；组合后容量是两输入之算术，产物类型随组合形态变化，用户须手算/宏推算容量；列/叶数量每次演进容量连锁改。七棵树 + workspace 私有模板的规模下，这是持续性人机工学税。
  - `LogicalDataType` 非 const 可构造（definition/mod.rs:157-181——`Timestamp{timezone: Option<String>}` 173、`Opaque{semantic_type: String}` 178-180 含堆 String）→ b 必须**全量**引入 const 镜像类型并在投影时转换（镜像类型 a 不需要、c 需要但只限形状负载）。
- **与现有 TbLayout 关系**：无耦合。
- **实现成本**：表面低、实际中偏高——容量泛型 + 全 const 化镜像 + 值→运行时投影桥接三层都要做。
- **下游适配**：模板是值不是类型，七棵树/私有模板的跨 crate 组合与引用全靠 const 命名纪律；文档导航、rustdoc 展示、错误定位都弱于类型形态。

### 1.4 候选 c：混合——结构 const 化 + 身份/挂载类型化 + 宏接线编译期检查

形态：

- **结构负载 const 化**：模板形状 = `&'static` 切片常量（条目表：域/层级域/表叶 + 槽位锚 + 列契约），即 §1.7 的 `TemplateSpec`。正交/合并判定、端点检查都在这份数据上以 const fn 完成（§2.3）。
- **身份与挂载类型化**：每个模板 = marker 类型 + `TreeTemplate` trait（`const NAME` + `const SPEC`）；挂载 = 组合声明里的 `(槽位, 模板类型, 角色标签)` 三元组（§3.3）。
- **组合宏接线**：`tree_compose!` 展开为——①复合模板类型 + `impl TreeTemplate`（`SPEC` = 结构化复合：宿主 + 挂载清单，**不做 const 扁平化折叠**，理由见 §2.1）；②一组 `const _: () = assert!(…)` 断言（正交冲突 / 端点存在与类型匹配 / 坐标系合法性）；③一个可编程访问的 `pub const CONFLICT: Option<ConflictReport>`（诊断/测试用）。

- **表达力**：七条语义全项覆盖——正交检查经 const 断言编译期可达（继承 b 强项）；多位置派生 = 类型身份 + mount 声明（继承 a 强项）；层级标注 = spec 数据；覆盖 = 声明序 fold（§2.4）。
- **与现有 TbLayout 关系**：零耦合（同 a/b）；投影桥独立函数（§5.2）。
- **实现成本**：中。一处 macro_rules 宏 + const 镜像类型 + 投影函数；无容量泛型（复合 spec 是结构化引用不是折叠数组）；`#![deny(missing_docs)]`（lib.rs:9）要求新公开面全量文档——计入但不构成风险。
- **下游适配**：最优——uni-mass-db 七棵树 = 七个 `TreeTemplate` impl（宿主公共根模板也是普通模板）；workspace 超集组合 = 一条 `tree_compose!`（workspace-定位.md §3 超集语义的模板层落点）；类型可导航、`SPEC` 可被 const 检查、成员模板可跨 crate 复用。

### 1.5 深比总表

| 维度 | a trait 泛型 | b const | c 混合（推荐） |
|---|---|---|---|
| 多位置派生（语义 7） | 类型级好 | 值级（无身份） | 类型 + mount 声明（好） |
| 层级标注叶子 | 关联 const 可 | spec 数据 | spec 数据（好） |
| 正交检查编译期可达 | **不可达**（稳定 Rust 无 negative reasoning） | 可达（const assert） | 可达（const assert + 宏接线） |
| 合并后到覆盖 | 泛型列表难保序语义 | 声明序 fold 可 | 声明序 fold 可 |
| 变长形状表达 | 关联 const 切片（无容量税） | **const 泛型容量税** | const 切片（无容量税） |
| 附加树无依赖裁决（R3'） | 类型级端点会引入定义期依赖 | 组合期检查可 | 组合期检查可 |
| 与 TbLayout/物理面关系 | 零耦合 | 零耦合 | 零耦合 |
| 投影到 DomainType/definition | 间接层多 | 值→值直投 | 类型取 SPEC → 值直投 |
| 实现成本 | 中偏高 | 中偏高（容量 + 全 const 化） | 中 |
| 下游（七棵树 + workspace 私有）适配 | 样板最重 | 命名纪律最弱 | 最优 |

### 1.6 拍板点①——推荐：候选 c（混合）

**推荐 c：结构 const 化（形状判定进编译期）+ 身份/挂载类型化（下游可导航、多位置有类型身份）+ 组合宏接线（诊断友好）。** 理由一句话：语义 5 的编译期正交检查在稳定 Rust 上只有 const-eval 一条路（a 被否决的直接原因），而 b 的 const 泛型容量税在七棵树 + workspace 私有模板的演进规模下不可持续——c 用"结构 const 化 + 类型身份"各取两家之长，且 01 §3.1 本就把载体预留为"Rust 类型/const 形态"（01:29）。

### 1.7 推荐载体 API 草案（可施工粒度）

新模块 `tree-space/src/template/`（纯增量；lib.rs 增 `pub mod template;` + 导出，其余文件零改动）。

```rust
/// 坐标系槽位名——newtype 而非封闭枚举：坐标系可扩展（语义 7，01:42）。
pub struct SlotName(pub &'static str);
impl SlotName {
    pub const STUDY: SlotName = SlotName("study"); // 现行
    pub const RUN:   SlotName = SlotName("run");   // 现行
    pub const LIB:   SlotName = SlotName("lib");   // 远期预留：只登记坐标，不落运行时映射（05:105）
}

pub enum ConstType { Bool, I(u8), U(u8), F(u8), Utf8, Binary, Date32,
    Ts { unit: ConstTimeUnit, tz: &'static str /* "" = None */ },

// 注：R1.5 的 List(Struct) geo vec 列与字段别名（类型体系扩展 01:4, 13-14）
// 在 ConstType 加变体/在 TemplateColumn 加 aliases 落地，归 R1.5 施工同步。

pub struct TemplateColumn {

    pub nullable: bool,

/// R7 索引声明占位：模板层持"声明了哪些索引"的 const 描述，
/// 具体 IndexSpec 类型直挂归下游 definition 面（10:21-27；policy 不进模板，见 §5.2）。
pub struct TemplateIndex { pub kind: IndexKindConst, pub columns: &'static [&'static str] }

pub struct TemplateTable { pub name: &'static str, pub version: u32,
    pub columns: &'static [TemplateColumn], pub indexes: &'static [TemplateIndex] }

pub enum TemplateEntryKind {
    /// 域节点。tier 仅为宿主模板声明实例化层级（对位 FamilyTier，family.rs:46-55）。
    Domain { tier: Option<TierDecl> },
    Table(TemplateTable),
}
pub struct TierDecl { pub prefix: &'static str, pub max_instances: u32 }

/// 模板内位置（§3.2）。
pub enum SlotCtx {
    /// 跟随挂载位置（多数业务内容）。
    Inherit,
    /// 绝对槽位锚（geo consensus = At(&[STUDY])，05:86）。
    At(&'static [SlotName]),
}

pub struct TemplateEntry { pub at: SlotCtx,
    /// 槽位锚之后的相对段（域嵌套路径，段名数组）。
    pub path: &'static [&'static str], pub kind: TemplateEntryKind }

pub struct TemplateSpec {
    /// 坐标系声明——仅宿主模板非空（slot → 父 slot + tier 参数）。
    pub coordinates: &'static [SlotDecl],
    /// 成员模板要求的槽位（组合期校验宿主坐标系覆盖，§2.3）。
    pub required_slots: &'static [SlotName],
    pub entries: &'static [TemplateEntry],

pub struct SlotDecl { pub slot: SlotName, pub parent: Option<SlotName>, pub tier: Option<TierDecl> }

/// 模板身份 trait。业务树/附加树/宿主完全同构（R3'：无依赖 DAG，05:55）。
pub trait TreeTemplate: 'static + Sync {
    const NAME: &'static str;
    const SPEC: TemplateSpec;
}
```

写法（uni-mass-db 点云树示意）：

```rust

impl TreeTemplate for PointCloudTree {
    const NAME: &'static str = "point-cloud";
    const SPEC: TemplateSpec = TemplateSpec {
```

施工前验证点（const 特性边界，M1 第一个 spike）：
1. 泛型 const fn 内读泛型参数关联 const（`fn check<T: TreeTemplate>()` 内用 `T::SPEC`）在目标工具链的稳定可用性——宏按**具体类型**展开断言可完全绕开该依赖（兜底成立，只影响辅助函数的泛型化程度）。
2. const panic 消息仅支持字面量——诊断信息由宏在展开期 `stringify!` 模板标识符编进字面量（冲突明细走 `CONFLICT` const）。

## §2 组合算子与编译期检查（拍板点②）

### 2.1 组合代数

组合单位三层：**宿主模板**（公共根，声明坐标系 + 层级域 + metadata 叶位，R0.5:66-69）× **挂载**（`(slot, 模板类型, 角色标签)`）× **模式**（Orthogonal | Merge）。

```
tree_compose! {
    pub template UniMassDbMvp = host(CommonRoot)
        mount(Run,   PointCloudTree)      // 点云挂 run（10:6.2）
        mount(Run,   GeoTree)             // geo：内部 consensus At(Study)（05:86）
        mount(Run,   ChemTree)
        mount(Run,   ChromatogramTree)    // 挂 run（05:101）
        mount(Study, SpectrumTree, as "reference")  // 参考谱位（05:97）
        mount(Run,   IonFormulaLink)      // 附加树：显式列出（05:55, 128）
        mode Orthogonal;                  // 或 Merge
}
```

**复合 SPEC 采用结构化形态**（宿主 SPEC + 挂载清单的 const 引用集合），**不做 const 期扁平化折叠**——折叠产生新 `&'static` 切片需要分配，const 期不可行，且正交判定只需遍历成员无需物化并集；扁平化物化发生在运行时投影（确定性 fold，§5.2）。

- 复合产物实现 `TreeTemplate` 吗？**v1 否**：复合 = 宿主 + 挂载清单，不是平铺条目表；下游要做"更大组合"时**重新声明一条 `tree_compose!`**（把原有成员再列一遍 + 新增私有挂载）——组合声明是廉价的、纯声明式的，复合嵌套列为 non-goal（避免两套复合形态）。
- 组合产物是**类型 + const**（编译期定死，语义 1）；不存在运行时组合 API（语义 3）。

### 2.2 冲突判定规则（05 R0 增补 ①②机械化）

对复合做确定性 fold（挂载声明序 = 先后序），在**具体逻辑路径**（槽位坐标路径 + 模板内相对路径，§3.1-3.2）上比较：

| 情形 | 规则（05:54 ①②） |
|---|---|
| **域重名**（两条目都解析为域节点且路径相同） | **合并**：两模式一致——子条目并集进入该域继续比较（域无自身内容，恒可合并） |
| **域 vs 叶同名**（同路径一方是域一方是表） | 结构性冲突：正交模式编译期报错；合并模式后到者胜（后者把该路径改为己方形态） |
| **叶子（表）重名** | 见下方解读呈报 |

**呈报（语义解读，需经理/用户确认）**：05:54 原文「②叶子重名 → 结构必须一致——正交模式编译期报错 / 合并模式后到覆盖」存在两种读法：

- **读法 A（本图纸采为工作假设）**：「结构必须一致」是叶子重名的**放行闸门**——正交模式下，同名叶**结构指纹完全一致**（列名/类型/nullable/id_component/indexes 逐项相等）→ 视为同一叶子的重复声明，**去重放行**；不一致 → 编译期报错。合并模式不设闸门：无论一致与否，后到者整体覆盖（列集/版本以胜者为准）。
- **读法 B（严格正交）**：正交模式下叶子重名一律报错（「结构必须一致」仅修饰合并模式的覆盖合法性）；合并模式后到覆盖。

两读法对 MVP 七棵树的实际差别趋近于零（各树叶子名现无跨树刻意重名；`links/` 域合并后各树表名互异），但机制边界不同（读法 A 允许"同叶子双声明"的幂等组合）。**建议按读法 A 落纸**（更符合「结构必须一致」作为独立闸门存在的行文），请拍板确认。

### 2.3 拍板点②——编译期报错机制：三选一

| 机制 | 判定 | 理由 |
|---|---|---|
| **类型系统** | **否** | 稳定 Rust 无 negative reasoning/specialization，无法对任意两模板形状做编译期相交判定；O(N²) 手写互斥 impl 不可扩展；下游每加模板都要动别的模板——违反组合的开放性 |
| **build.rs 检查** | **否** | 声明需要第二表示（打破单一事实源）或 build 期编译运行生成器（复杂、慢、IDE 不友好）；检查点与声明点在开发者心智里分离 |
| **const-eval 断言（宏接线）** | **是（推荐）** | 模板形状已 const 化（§1.4）→ const fn 谓词 + `const _: () = assert!(…)` 编译期报错，稳定可用；宏在展开期把模板标识符 `stringify!` 进字面量消息，报错定位在**组合声明处**（正确的责任位置）；冲突明细经 `pub const CONFLICT: Option<ConflictReport>` 可编程访问 |

推荐形态：`tree_compose!` 为每个复合生成一组 `const ORTHO_CHECK: () = { … assert!(…, "orthogonal violation while composing <Composite>: see CONFLICT") };`。检查项与时机全表见 §2.6。

**纵深防御不变**：运行时类型面既有校验全部保留（`TypeRegistry` 同名同版异构拒绝 registry.rs:109-121, 140-153；组合展开冲突 registry.rs:574-580；manifest checker）——编译期报错是**新增前置闸门**，不是替换运行时校验（语义 6 读侧宽容不受影响：宽容针对"实例数据超出声明"，声明面本身仍严格校验）。

### 2.4 合并形态（后到覆盖）语义细则

1. **覆盖单位 = 叶子声明整体**：后到模板的同路径表叶（列集/版本/索引声明）**整叶替换**先到者——不做表级/列级部分合并（避免混合指纹面；与 07 历史 §5.2 的定义级覆盖最小语义同思路，该节为历史记录，见 MVP 03:68-70）。
2. **覆盖顺序 = 组合声明序**（fold 序），宏展开确定、无运行时仲裁。
3. **覆盖是声明面语义**：数据块不动（内容寻址）、实例行为不变（语义 2/3；01 §4 不改实例层）。覆盖后的运行时对账由既有 manifest checker 承担（旧 definition 对被覆盖段的写入被拒——既有机制，06 调研 §2-4）。
4. **域重名恒合并**（两模式一致，05:54 ①）；合并模式下"覆盖"只发生在叶位。
5. 模式是**复合级**的（一条 `tree_compose!` 一个 mode）；不做 per-mount 混合模式（语义 5 只定义了两模式；混合模式列 non-goal，需要时未来再立项）。

### 2.5 附加树端点的组合期检查（R3' 落机制）

- 附加树的 link 表列声明可带 `points_to: Option<EndpointRef>`（`EndpointRef { template: &'static str, leaf_path, column, expect: ConstType }`）——**模板定义期不解析它**（附加树单独存在完全合法，机制上与业务树平权，05:55）。
- `tree_compose!` 对复合内**出现的**每个带 `points_to` 的列发出 const 断言：被指 `(template, leaf, column)` 在**本复合**中存在且 `ConstType` 匹配——被指模板未参与组合 → 编译期报错（"ion-formula-link requires point-cloud in this composition"）。
- 这正是 R3' 的「跨树链接的端点兼容性检查归组合期……不是模板定义期的类型依赖」（05:55）的机制化。

## §3 多位置派生与挂载坐标系（第七语义机制化，01:40-42）

### 3.1 槽位坐标系

- 坐标系 = **槽位的有序层级声明**，由**宿主模板**的 `coordinates` 承载：现行 `study`（根级）→ `run`（study 之子）；远期 `lib`（根级预留，05:105——本期只登记 `SlotName::LIB` 常量，不落运行时映射）。
- newtype `SlotName(&'static str)`（§1.7）保证**坐标系可扩展**：workspace 宿主可声明自有私有槽位（如会话/缓存域）；跨 ecosystem 组合时，成员模板的 `required_slots` 必须被宿主坐标系覆盖（编译期检查，§2.6）。
- 具体逻辑路径 = 槽位坐标路径 ++ 模板内相对路径；槽位坐标路径由宿主坐标系唯一确定（如 run 级内容 = `[study, run]`）。**正交/合并判定全部发生在具体逻辑路径上**——同一模板挂不同槽位时路径天然不同、天然正交。

### 3.2 模板内位置标注（层级标注叶子）

- 条目级 `SlotCtx`：`Inherit`（跟随挂载位置）/ `At(&[SlotName])`（绝对槽位锚）。
- 先例驱动：R2 #4 geo 树 = run 级 geo domain + **study 级 consensus 表**（05:86，a 方案「跨层级叶子」）→ geo 模板内 consensus 条目 `At(&[STUDY])`、其余 `Inherit`，整树挂 `Run`——一条模板两种层级一次表达。
- `At` 锚的合法性在组合期校验（宿主坐标系须含这些槽位）；成员模板用 `required_slots` 声明自己需要的槽位（编译期检查宿主是否满足，§2.6）。

### 3.3 同模板多位置挂载 + 语义角色注入

- **同模板多位置**：`mount(Study, SpectrumTree, as "reference")`（现行，参考谱位）与远期 `mount(Lib, SpectrumTree, as "library")`（独立库资源位，05:97）——**同一个 `TreeTemplate` 类型，两条 mount 声明**；「多张库 = 多位置实例、库分组由挂载路径承载、不实体化 library 列」（05:97）由"lib 槽位下的实例化层级"承载（宿主为 lib 槽位声明 tier 即得，机制同 study/run）。
- **语义由位置注入**：挂载声明三元组的第三元 `as "label"` 是**编译期角色标签**——进入复合的挂载清单（const 可查），并作为**投影注解**（definition 侧描述/manifest 值的候选来源）传给下游；**不进入数据 schema、不实体化为列**（与 05:97「不实体化 library 列」同纪律）。角色是否持久化为运行时注解 = 下游 MVP 工单拍板项（§5.2 分工表）。
- 同槽位重复挂载同一模板 = 叶子路径必然交叉 → 正交模式编译期报错（符合直觉：同位双挂无意义）；合并模式 = 后者整叶覆盖（仍允许，但无场景）。

### 3.4 与物理路径方案解耦

- 模板层只讲**逻辑槽位坐标**；物理路径方案（uni-mass-db 现行 owner 外置 `o{owner}/s{N}/r{M}`，writer.rs:31, 571-572 派生段名；R0.5 提议的 `/{study}/r{run}/o{tree}` 反转——**待用户最终确认**，05:67, 72）是 **persist 层映射参数**，不进模板层。
- 因此 R0.5 两个待确认项（结构反转、run 注册表合并形态）**不阻塞本图纸**：无论反转与否，模板层产出的都是同一份槽位化路径事实；投影函数带映射参数（现行 owner-outer 映射 / 反转映射），参数归下游 MVP（§5.2/§5.4）。

## §5 与 uni-mass-db definition 的映射（MVP 重设计 §M0-4 联动）

### 5.1 双层关系裁定建议

**裁定建议：definition = 模板的运行时投影 + 校验目标（单向：模板 → definition；运行时永不反向生成模板）。**

- **模板 = 编译期权威**：树形、槽位、叶子列契约（name/ConstType/nullable/id_component/aliases/indexes 占位）、挂载与角色——编译期定死（语义 1），是 R1-R8 各域推导的**落纸载体**。
- **definition（uni-mass-db `DatabaseDefinition`）与 tree-space 类型面（`DomainType/TableType`）= 运行时值**：它们是 open/check_manifest 的对账基准（family-meta `(TypeId, version)` 逐条比对，06 调研 §2-3）与 TypeRegistry 注册实体（registry.rs:107-154）——运行时身份面必须以"值"存在并随库走，不能被编译期类型替代。
- 两层各自不可缺，**桥梁 = 投影函数**（§5.2）；「definition 是模板的运行时投影」与「definition 是校验目标」二者**同时成立**：投影生成 definition 值 → 既有校验器（definition validate / TypeRegistry / manifest checker）照常消费它。这是"校验目标"的准确含义——不另造模板↔definition 的第三套校验。
