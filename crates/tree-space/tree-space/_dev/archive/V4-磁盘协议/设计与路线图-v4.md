# 第一部分：架构规范

## 1. 定位、边界与规范性词汇

`tree-space` 是面向 Arrow 表集合的**通用、可持久化、可恢复、并发安全、可验证**的表空间内核。它不包含质谱、mzML、IonStream 或其它领域语义；它只提供领域无关的类型注册、路径、实例身份、事务、metadata、三布局、文件锁、digest、verify、同步和服务协议。

### 1.1 分层边界

| 层 | 负责内容 | 不负责内容 |
|---|---|---|
| `uni-mass-db` | 在 `tree-space` 之上构建业务 definition、业务 metadata 表、validators、业务查询/操作 API | 磁盘格式 ABI、跨进程锁协议、事务内核、布局、digest、verify |
| 领域 crate | 具体 domain/table 定义、数据导入、转换规则、业务校验 | 重复实现 manifest、布局、哈希和同步 |
| 应用/服务 | 权限策略、网络传输、UI、任务调度 | 直接修改磁盘内部结构 |

`tree-space` 的输入与规范内存表示是 Arrow。上层（如 Polars）可以是计算运行时，但进入 `tree-space` 前必须转换为 Arrow，并在写路径上按 Arrow schema 校验。

### 1.2 规范性词汇

- **必须（MUST）**：违反即格式不兼容、数据不安全或测试不合格；
- **应当（SHOULD）**：默认要求；偏离时必须有明确原因与测试；
- **可以（MAY）**：可选优化，不得改变已定义语义；
- **写路径**：`create`、`write`、`rename`、`publish`、`gc`、`migrate`、`repair`；
- **读路径**：`open`、`resolve`、`snapshot`、`wait`、`verify`；
- **发布**：新数据已经完整可读、元数据已登记、可被新读者解析的原子状态切换。

## 2. 兼容性与依赖契约

### 2.1 Rust 与 mzparse 兼容性

`mzparse/rust/Cargo.toml` 声明 `rust-version = "1.89"`。因此 `tree-space` 必须使用同一 MSRV：

```toml
rust-version = "1.89"
edition = "2024"
```

MSRV 1.89 是采用 `std::fs::File` 原生文件锁（`try_lock` / `lock_shared` / `unlock`）的前提，用于消除对 `fs4` 等第三方锁依赖。根仓库 Pixi `dev-all-gpu` 当前提供较新 Rust，用于日常构建和测试；不是降低 MSRV 的理由。`rust-189` Pixi 环境固定 `rust ==1.89.0`，是 MSRV 门的事实来源。

### 2.2 已冻结的基础依赖

| 依赖 | 角色 | 约束 |
|---|---|---|
| `arrow = 55`（`ipc`） | Field IPC、RecordBatch IPC、特殊表与容器段 | 与 mzparse 的 Arrow 主线一致 |
| `memmap2 = 0.9` | M0/M3 只读映射测试与单文件映射 | 任何 `unsafe` 映射局限在布局模块 |
| `tempfile = 3.14` | 端到端测试库与故障注入 | 不进入运行时 API |

文件锁使用 `std::fs::File` 的 1.89+ 原生 API（`try_lock`/`lock_shared`/`unlock`），不引入 `fs4` 等第三方锁依赖。

## 3. 核心不变量（MUST）

1. 已发布 snapshot 不可变。
2. 任何成功 `write` 必须持久化 payload + metadata + digest；仅更新进程内缓存不算发布。
3. `open()` 必须恢复出与最后一次成功发布等价、可解析、可验证的逻辑库。
4. layout 发布成功前新 runtime snapshot 不可见；失败后读者只能看到完整旧快照或完整新快照。
5. metadata 是唯一 authority；内存 `BTreeMap` 只是缓存。
6. verify 必须只读、可复算真实存储 digest，不依赖进程内缓存。

## 4. 通用业务无关元模型

- 稳定 `TypeId` / `NodeId` / `TableId` / `PathHash` / `SchemaVersion`。
- table schema 用 Arrow IPC fields 表达。
- 通用 key/value extension metadata，供业务库放置语义数据。
- path 与 type identity 分离。
- **path 段（`Name`）为 UTF-8 可见文本**：长度 1–64 字节，仅拒 `/`（路径分隔）、`%`（转义）、ASCII 控制字节、空段与保留名（`manifest`/`dt_*`/`tt_*`/`table-metadata`/`domain-metadata`/`column-digests`/`.`/`..`）。**禁止以 path 命名物理文件**：布局 blob 一律按 `table_id` 内容寻址命名，path 只作逻辑键与 `PathHash`/digest 输入，故 UTF-8 不碰文件系统命名、不影响冻结字节。
- schema/type version 迁移策略先定义后实现。

### 4.1 必须存在且可读写的权威表

- `table-metadata`：每个已发布表实例的权威记录（id、path、type、创建/更新、owner、extension）。
- `domain-metadata`：domain 实例级权威记录。
- `column-digests`：列级 digest 权威记录。

`registry_from_tables` 只重建 type definitions 是不够的；这些表必须在 `open()` 时被恢复并用于重建 slots/table_types/locators/digests。

## 5. 事务模型（PreparedCommit）

每个成功发布必须走统一 `PreparedCommit`：

1. schema 校验与 payload materialization；
2. metadata delta 生成；
3. digest delta 生成；
4. ownership/metadata 记录；
5. 获取布局锁；
6. layout commit（payload、metadata、digest、可见性点原子可见）；
7. receipt 返回；
8. runtime 原子 install；
9. 失败即 abort/recovery，内存状态保持旧 snapshot。

### 5.1 可见性顺序

- 先持久化后可见：layout commit 成功前，任何 `snapshot/resolve/wait` 不得返回新状态；
- layout commit 失败时，内存必须回滚到与上一成功发布一致的状态。

## 6. 三布局等价语义

Memory、SingleFile、ParquetDir 必须共享**同一个逻辑 snapshot**，不允许各自偷换语义。磁盘格式只负责物化同一份逻辑状态。

| 布局 | 角色 | 格式要求 |
|---|---|---|
| Memory | 唯一正确性 reference | 与逻辑 snapshot 1:1 |
| SingleFile | 真实追加容器 | payload segments → metadata segments → epoch directory（table locators）→ trailer |
| ParquetDir | 目录 snapshot（content-addressed commit-tree） | `tables/<table_id>-<content_hash>.parquet` 不可变 blob；`committed` 指向 commit → tree（`{table_id → content_hash}`）→ blob；GC = 可达性树压缩 |

### 6.1 Parquet-dir 原子性（content-addressed commit-tree）

parquet-dir 采用 git 式**内容寻址 + commit 树**实现整库原子视图、跨历史去重与可回收性。核心是 v3 §9"指针相等 ⇒ 复用"从 digest 层延伸到物理存储层：

- **blob**：表内容存为不可变文件 `tables/<table_id>-<content_hash>.parquet`，按内容寻址、**跨提交去重**——重写为相同内容的表复用同一 blob，零新增、零重算；blob 永不原地覆盖；
- **tree**：一张小 Arrow 表，记录逻辑快照 `{table_id → content_hash}`（表定位即 locator 来源）并引用对应 metadata 快照；
- **commit**：`{sequence, parent, tree_id, metadata_ref}`，沿 parent 形成修改树/DAG；
- **`committed` 是唯一可见性点**：指向当前 commit（= HEAD），发布时**最后**原子替换；读者只读当前 commit 树命中的 blob → 永远得到整库原子视图；
- **`manifest` 保持冻结 boot 标记**，不承担可变可见性指针；
- **覆盖的唯一形态**：写新 blob → 建新 tree → 建新 commit → 原子切 `committed` → **立即触发 GC**（保留窗口=1）；没有独立的"原地覆盖"物理路径；
- GC = 可达性树压缩（见 §6.2）；
- **与 PreparedCommit 的映射**：§5 第 1–4 步（校验/物化/digest/metadata delta）在内存完成；第 5 步取布局锁；第 6 步 layout commit = 写新 blob → 写新 tree → 写新 commit → **原子替换 `committed`**（前序对象内容寻址、不可变，即使 `committed` 未切换也只是成为孤儿，由 GC 收回）；第 7 步返回 receipt；第 8 步 runtime install；第 9 步失败即回滚内存到旧快照，孤儿对象留给 GC——原子性由"最后才切 `committed`"保证。

### 6.2 GC = 可达性 + 树压缩

GC 不是可选优化，而是 commit-tree 存储的收尾步骤（MVCC 固有代价），但回收粒度与增长速率比 epoch 全量快照合理得多：

- **可达性标记**：以保留基点（当前 `committed`，可沿 parent 回溯到保留窗口 `keep_from_sequence`）为根，标记可达的 blob/tree/commit；
- **淘汰**：回收不在可达集内的对象；被当前 `committed` 直接或间接引用的对象**永不删除**（sidecar/活数据不 rename/delete 纪律）；
- **树压缩（repack）**：可选将活对象重写为紧凑形式后重建 `committed`，等价 git gc；
- **覆盖 = 保留窗口 1 + 立即回收**：无历史需求的表，GC 把旧 blob 即刻回收，对外表现"原地覆盖"，内部仍是写新 blob + 切指针 + 回收旧 blob；
- GC 必须排除当前快照引用，绝不破坏原子性（见不变量 #4）；
- **crash 安全**：GC 在布局写锁下运行，可达集从当前 `committed`（+保留窗口）计算，该 `committed` 在 GC 期间不被改写（写锁互斥）→ GC **永不删除可达对象**；sweep 中途崩溃只留下"未删干净的不可达对象"，幂等、下次 GC 续收，绝不误删活对象；
- **避开活跃读者**：GC 跳过仍有存活引用（`TableSlot` 借用快照 / mmap 句柄）的对象，保证读者已持有句柄不受影响（旧快照 Arc 自然存活）。

### 6.3 磁盘对象、命名与字节级协议（冻结）

parquet-dir 所有对象均为 Arrow IPC 或 parquet；对象 id 一律由内容派生（content-addressed），使对象自校验并按可达性回收。

**目录与命名：**

| 对象 | 路径 | 说明 |
|---|---|---|
| blob | `tables/<table_id>-<content_hash>.parquet` | 不可变，zstd；按表内内容去重 |
| tree | `trees/<tree_id>.ipc` | 全库 `{table_id → content_hash}` 映射 |
| commit | `commits/<commit_id>.ipc` | 修改树节点 |
| metadata | `metadata/<metadata_ref>/` | 9 张特殊表 `<name>.parquet` |
| committed | `<root>/committed` | 唯一可变可见性点，稳定路径，tmp+rename 原子替换 |
| sidecar 锁 | `locks/…` | 不参与对象回收，永不 rename/delete |

**对象 id（均为 `canonical_digest`，见 §8.1）：**

```
content_hash = canonical_digest(b"content", [type_id, version, (col_order||完整列规范化IPC)…])
tree_id      = canonical_digest(b"tree", [ (table_id||content_hash)… ])
metadata_ref = canonical_digest(b"metadata", [ (特殊表名||其规范化IPC)… ])
commit_id    = canonical_digest(b"commit", [sequence, parent, tree_id, metadata_ref])
```

- `content_hash` 的"完整列"= 跨 RecordBatch `concat` 拼接后的整列规范化 IPC（**含 `in_hash=false` 列**），切分无关；
- `content_hash` 面向**规范化 IPC bytes** 而非 parquet bytes（写法在内存算好，符合"永不计算文件字节哈希"）；blob 落盘为 parquet，逻辑等价即共享同一地址；
- tree/metadata/commit 均按确定性顺序排序后取哈希。

**对象 Arrow schema：**

| 对象 | 列 |
|---|---|
| tree | `table_id: FixedSizeBinary(16)`, `content_hash: FixedSizeBinary(16)` |
| commit | `sequence: UInt64`, `parent: FixedSizeBinary(16)`, `tree_id: FixedSizeBinary(16)`, `metadata_ref: Utf8` |
| committed | `head_commit_id: FixedSizeBinary(16)`, `sequence: UInt64`（单行） |

**完整性：** 内容寻址对象在加载时重算 id 与文件名比对即自校验；`committed` 是唯一非内容寻址对象，其有效性 = 加载 head commit 并核对 `commit_id`。以上均为协议字节，必须冻结 golden（见 §8.2、§21）。

## 7. open / recovery

- `open()` 读 `committed` → head commit → 得 `metadata_ref`（加载 9 张特殊表）与 commit → tree → 得 `{table_id → content_hash}` locator，并结合 `table-metadata` 重建 slots、table_types、locators、digests；
- 未加载 slot 使用 lazy locator loader；
- 处理 truncation、corrupt trailer/commit/committed、corrupt parquet、interrupted commit；
- rollback 到最近完整有效 revision（沿 parent 回溯）。

## 8. digest 与内容寻址（双哈希，不可混用）

- canonical Arrow bytes；必须跨 RecordBatch 切分稳定；
- 区分 storage digest 与 extension/business digest；
- 定义 column/table/domain/root digest 更新规则；metadata 自指排除；
- `verify` L3 必须使用正式 `table_digest`，不得使用与发布无关的自造 label。

**双哈希铁律**（parquet-dir 内容寻址的关键）：
- `content_hash` = 全内容哈希（**含 `in_hash=false` 列**），仅用于 blob 寻址/去重；公式见 §6.3；由写入方在内存算好随表落盘，**永不计算文件字节哈希**；
- `table_digest` = 语义 Merkle digest（仅 `in_hash` 列），仅用于 verify/哈希树；
- **禁止以 `table_digest` 当存储地址**——否则两张仅差在 `in_hash=false` 列的表会同地址碰撞丢数据。

### 8.1 canonical_digest 与层级公式（唯一实现）

`canonical_digest(tag, parts)` 是唯一规范化原语：长度前缀的域标签 + 长度分隔的部分序列，再取 xxh3-128：

```
canonical_digest(tag, parts) = xxh3_128( len(tag)||tag || len(p1)||p1 || … || len(pn)||pn )
```

- 列：`column_digest = canonical_digest(b"column", [type_id, version, col_order, field_ipc, 列规范化 IPC])`；`in_hash=false` 的列不产生 digest；
- 表：`table_digest = canonical_digest(b"table", [type_id, version, (col_order||col_digest)…])`，按 col_order 拼接 in_hash 列 digest；
- domain：`domain_digest = canonical_digest(b"domain", [node_id, (kind||name||child_digest)…])`，子部分按 (child_order, 实例名字典序) 聚合；
- **空 domain**：`empty_domain_digest = canonical_digest(b"domain", [])`（零子部分的固定常数），不得另造标签；
- 特殊表不参与哈希树（防循环定义），其完整性由 L1 与 trailer/committed checksum 覆盖。

### 8.2 golden 冻结

`canonical_digest` 与其各层级公式、以及 §6.3 的对象 id 派生必须由 golden 测试对固定输入断言精确 16 字节输出；任何 Arrow 编码或哈希改动必须同步更新 golden 并大声报警。

## 9. 并发

- in-process reader/writer 可见性；
- cross-process writer ownership；
- lock granularity（整库 vs 表级）；
- commit ordering；
- crashed writer 语义；
- `std::fs::File::lock`（1.89+）是唯一锁后端，sidecar 路径不得 rename/delete。

## 15. M4 关闭标准

Single-file 真实包含 payload segments、metadata segments、epoch directory 与 trailer；reopen 恢复；截断、损坏 checksum、伪造 previous offset、中断发布等故障可恢复或明确报错。

## 16. M5 关闭标准

Parquet-dir 中间失败时读者只见完整旧集合；`committed` 是唯一可见性点并指向 commit → tree → blob；相同内容重写共享同一 blob（去重断言）；reader 前后不可见中间态；sidecar 永不 rename/delete；每表并行写不同表、竞争写同表可测；GC 按可达性只回收 unreferenced blob/tree/commit/metadata，且覆盖（保留窗口 1 + 立即回收）后的对外快照与 Memory 等价；§6.3 对象字节协议有 golden 冻结。

## 17. M6 关闭标准

open 后从未加载 slot 重建到可 resolve；lazy loader 按 locator 读 payload；wait(generation) 因果语义正确；clean/dirty/unload 状态机明确。

## 18. M7 关闭标准

column/table/domain/root digest 决策性；RecordBatch 切分不影响 digest；std sidecar 锁跨进程；进程终止后锁恢复；`lock_unavailable` 与 `replace_blocked` 正确区分。

## 19. M8 关闭标准

verify 只读；L2 schema、L3 正式 table_digest；子树 scope；报告 Arrow schema；verify 前后文件 mtime 与根 digest 不变。

## 20. M9–M12 关闭标准

- M9：根 digest 差异下钻、零变化零传输、随机编辑后收敛；
- M10：六条转换规则、dry-run 无写入、覆盖检查、标准发布；
- M11：memfd/named mapping、句柄传递、读者稳定性、持有者终止、无人引用回收；
- M12：受理序号、全局屏障、五动词 API、拒绝分类、嵌入式/服务模式语义等价。

## 23. 首批实现任务（Phase A–C）

7. **open/recovery**：从 metadata 重建 slots/table_types/locators/digests；处理截断、损坏、中断发布。
8. **digest/verify 对齐**：正式 table_digest 跨 batch 切分稳定；verify L3 使用正式 digest；verify 前后只读。
9. **跨进程/故障测试**：为上述每个闭环补充 golden、property、fault、e2e 测试。
